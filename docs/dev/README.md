# 开发侧协作文档

## 首要原则：仓库是唯一的同步通道

设计工作在另一个对话里进行，开发工作分散在更多对话里。
**对话之间互相看不见**，所以不要指望靠"说一声"来同步。

设计变更只有落到仓库里，开发才看得到；开发进度也只有写回仓库，设计才知道哪些已经动工。

| 文件 | 主要维护方 | 作用 |
|---|---|---|
| `docs/design/CHANGELOG.md` | 设计侧 | 每次设计变更记一条，写明影响哪些模块 |
| `docs/dev/模块对接表.csv` | 双方 | 设计模块 ↔ 配置表 ↔ 代码路径 ↔ 状态 ↔ 目标设计版本 |
| `data/tables/` | 设计侧 | 数值的唯一来源 |
| `docs/dev/当前状态.md` | 开发侧 | **一页看板**：一条命令怎么验、现在能玩到什么、待外部输入清单（含「到位后改哪里」） |
| `docs/dev/平衡观测.md` | 开发侧（给设计侧看） | 当前数值跑出来的胜率／收益快照，含口径与复现命令；**只读观测，不是门限** |
| `docs/dev/上下文与压缩.md` | token 优化那一条线程 | **查询线程的寿命**：每轮 token 怎么量、为什么会涨到 60 万、自动压缩阈值配在哪两个全局文件、阈值怎么选（根 `AGENTS.md`「主动退休」的展开） |

三者的关系：

```
设计变更 ──► CHANGELOG 记录影响模块
                  │
                  ▼
          模块对接表：把受影响模块的
          design_version 与新版本对比
                  │
                  ▼
          版本落后且已动工 ──► 标记「需返工」
```

## 开工前必做

1. 读项目根目录的 `AGENTS.md`
2. 读 `docs/design/CHANGELOG.md`，看最近有没有改动你负责的模块
3. 在 `docs/dev/模块对接表.csv` 里找到自己的模块，确认 `design_version`
4. 如果设计版本比对接表里记的更新，先评估要不要返工，再动手

## 开工后

- 代码路径定下来后，回填对接表的 `code_paths` 列
- 状态变化及时回写（`未开始` → `进行中` → `已完成`）
- **数值一律从 `data/tables/` 读，不要在代码里写死**
- 发现设计有问题，**不要私自改表**——改 `docs/design/` 下的文档，并在 CHANGELOG 记一条，让设计侧确认

## 设计变更后怎么响应

| 情况 | 动作 |
|---|---|
| 你的模块 `design_version` 落后，且状态为 `未开始` | 直接用新版本开工，把 `design_version` 更新到当前版本 |
| 落后，且状态为 `进行中` | 暂停，评估已完成部分的返工量，把状态改为 `需返工` 并写清原因 |
| 落后，且状态为 `已完成` | 评估是否必须返工。必须返工则改 `需返工`；不影响则更新 `design_version` 并注明 |
| 模块被设计侧标为 `已冻结` | 不要动。要改先在设计文档里提，走一次正式变更 |

## 对接表字段

| 字段 | 说明 |
|---|---|
| `module_id` | 模块唯一标识，代码里也用这个名字命名目录 |
| `module_name` | 中文名，给人看的 |
| `design_docs` | 对应的设计文档，多个用 `\|` 分隔 |
| `data_tables` | 依赖的配置表，多个用 `\|` 分隔 |
| `code_paths` | 代码路径，开工后回填，多个用 `\|` 分隔 |
| `status` | 见下方状态定义 |
| `design_version` | 该模块当前对齐到哪个设计版本 |
| `note` | 备注，**不要用英文逗号** |

## 状态定义

| 状态 | 含义 |
|---|---|
| `未开始` | 还没动工 |
| `进行中` | 正在写 |
| `已完成` | 写完并自测通过 |
| `需返工` | 设计变了或发现缺陷，需要改 |
| `已冻结` | 设计侧锁定，改动需走正式变更流程 |

## 校验

`tools/validate_tables.ps1` 会顺带检查对接表：

- 引用的设计文档和配置表是否真实存在
- 状态值是否合法
- 已动工的模块是否落后于当前设计版本（落后会报警告）

所以**对接表不是文档，是会被检查的数据**，乱填会红。
