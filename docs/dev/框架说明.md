## 启动菜单与存档

主场景是启动菜单，三个入口都是真实功能：

| 入口 | 行为 |
|---|---|
| 新建游戏 | 从 `character_base.csv` 取队伍（最多 4 人）→ 建 `GameState` → 写进第一个空存档槽 → 进入游戏 |
| 读取存档 | 列出 6 个槽位的队伍／等级／难度／保存时间；损坏档标为「存档损坏」并置灰；点一份就载入并进入游戏 |
| 退出游戏 | 结束进程 |

细节：

**存档字段的「全字段往返」断言**：`tests/test_save_store.gd` 会把**每一个**存档字段都设成非默认值，
落盘再读回，递归比较两份 `to_dict()`（差异会打印出具体路径，例如 `root.char_hp.scholar_fallen（读回时丢了）`），
并钉住 `to_dict()` 的字段数（现在是 **27**）——加字段只加一半（写了没人读／读了没写）会立刻红。
这条断言做过「把 `_read_char_hp` 摘掉」的反向验证，确认它真的会报，而不是永远绿的摆设。

- 存档目录默认 `user://saves`，可用项目设置 `lunhui/save_dir` 或命令行 `-- --save-dir=<路径>` 覆盖（后者是给受限环境跑真实场景自检用的）。
- 槽位满了以后，先回收**损坏**的存档槽，再覆盖**最旧**的可用存档；空槽永远优先。
- 存档目录不可写时不挡着玩：照常进入游戏，只是提示「本次进度不会保留」。
- 存档是纯 JSON（`GameState.to_dict()`），不含 Resource 引用。当前版本 **v15**：
  v1 只有队伍与难度；v2 加背包／加点／队伍经验；v3 加武学熟练度；v4 加已学武学与装配；
  v5 让装备实例带上随机词条；v6 加商店交易状态（累计买入次数与回购列表）；
  v7 加副本完成度永久记录与抽卡保底计数（保底从此跨战斗、跨难度继承）；
  v8 加大地图揭开记录（`revealed_nodes`）；v9 加事件判定记录与剧情旗标（`event_checks` / `flags`）；
  v10 加首杀掉落记录（`first_kills`，某个掉落组只领一次首杀奖励）；
  **v11 加战斗外气血**（`char_hp`，医馆治疗要按「缺失气血」收费）；
  **v12 加战斗外增益**（`field_buffs`，存绝对到期时间戳，退出重进照现实时间继续走）；
  **v13 加大地图坐标**（`world_pos`，读档一律回大地图、落在存下来的那个点上）；
  **v14 加天赋与自建模板**（`talent_picks` / `custom_templates`）；
  **v15 加 NPC 好感**（`npc_favor`，赠礼／切磋／偷窃／兑换都会改它）。
  读老档时自动补齐缺的部分（v1 补初始装备与空背包，v1~v3 补「已学 + 装配」），
  然后按当前版本写回（`MenuController.load_game` 负责回写）。
- 界面入口：游戏内场景的「角色与行囊」按钮或 **Tab** 键；界面内 ESC 返回游戏。

### 背包与装备

| 内容 | 约定 |
|---|---|
| 物品堆叠 | `item_base.stack_max` 为上限，超出部分回报为 overflow；`is_key_item=1` 的道具禁止丢弃 |
| 装备实例 | id 形如 `eq_sword_01#3`，序号存在存档里；本体数值仍来自 `equip_base` |
| 穿戴 | 槽位容量取 `equip_slot_def.max_equip`（戒指 2）；空位优先，满了替换第一格 |
| 穿戴限制 | 角色等级 ≥ `level_req`；武器槽只能装模板 `weapon_type` 的武器（设计说「模板决定可用武器类型」） |
| 属性加成 | `attr_*` 走属性点层、`bonus_*` 走固定值层，通过 `Inventory.contributions_for` 交给 `AttributeCalculator` |
| 战斗联动 | 战斗单位统一由 `PartyBuilder.build_actors(db, state)` 构造，所以穿戴与加点一定进战斗 |

### 角色面板的判定值

非战斗技能与事件判定按设计只用**裸属性**（模板 + 加点，不含装备）：
`attr:x` 取裸值，`skill:y` = 技能等级 + `floor(相关裸属性 / 5)`。面板上固定标注「判定值不含装备加成」，
用例里也钉了「换装不改变判定值」这一条。
- 界面骨架除了**战斗界面**以外仍用代码搭（占位美术阶段的取舍），美术到位后再逐个搬进 `.tscn`；
  战斗界面已经搬完，见下面「界面骨架与版式预算」。

### 装备词条

掉落出来的装备带随机词条（`src/core/affix_roller.gd`），规则全在表里：

| 内容 | 出处 | 约定 |
|---|---|---|
| 词条数量 | `rarity_def.affix_min/affix_max` | 凡品 0~1、良品 1~2、珍品 2~3、奇珍 3~4、传世固定 4 |
| 槽位限定 | `affix_pool.allow_slots` | 武器刷不出「气血上限」，护甲刷不出「破架势」 |
| 稀有度门槛 | `affix_pool.min_rarity` | 词条只出在够档的装备上（`af_luk_01` 要珍品起） |
| 数值 | `affix_pool.value_min/max` + `weight` | 按权重不重复抽取；`attr_point` 取整，其余保留 3 位小数 |
| 存档 | 实例里的 `affixes` | 存 `{affix_id, target, value_kind, value}`：**滚好的数值冻结**，设计改词条池不会改坏已刷出来的装备 |
| 生效 | `Inventory.contributions_for` | `attr:` → 属性点层，`stat:` → 固定值层，与装备本体的加成走同一条通道 |

词条是「刷」的核心，所以随机必须可复现：`AffixRoller` 吃一个 `RngService`，
战斗界面用同一个种子同时驱动战斗与词条（`--battle-selftest` 与用例靠它拿稳定结果）。
宝箱掉落同样会滚词条（`local_map_controller` 显式传一个随机源）。

### 存档时机

设计 02「存档规则」写得很清楚，但以前**一条都没实现**——只有「新建游戏」落过一次盘，
之后打的等级、加点、装备、完成度、商店交易全在内存里，退出即丢。现在按表照做：

| 地点 | 设计 | 实现 |
|---|---|---|
| 城镇 | 存档点，可自由存读 | 小地图里按 **F5** 手动存（`save_game`）；占位枢纽场景加了「保存游戏（F5）」按钮 |
| 大地图 | 切换小地图时自动存档 | `OverworldController.enter_local_map()` 里存一次 |
| 副本内 | 自动存档，退出重进不掉本层进度 | 清房间（战斗结算）、开宝箱、触发隐藏内容、事件判定、扫荡 各存一次 |

统一走 `src/core/save_service.gd`：`save(原因, 是否自动)` → 写当前槽（`state.slot`），
记下原因供状态栏播报（「已自动保存（开宝箱）」）。**读档仍只在主菜单**——
存档槽列表已经在那儿，游戏内再写一套只会两处打架；城镇的「可自由存读」读档部分留给主菜单的槽位列表。
没有存档槽（例如测试里临时开的局）时 `can_save()` 直接拒绝，不会往磁盘上写半截东西。

用例注入临时目录（`save_store_override` / `map.save_store_override`）来验证落盘，
正常流程用 `SaveStore.default_dir()`（`--save-dir` → 项目设置 → `user://saves`）。

### 完成度界面与扫荡入口

完成度以前只有 HUD 一行；设计 03 要求「副本界面显示完成度……作为玩家的追求目标与炫耀项」，
所以补了 `scenes/dungeon_screen.tscn`（副本里按 **M** 打开）：

| 区域 | 内容 |
|---|---|
| 摘要 | `总计 33%（4 / 12 项）`，全清会写「—— 全部完成！」 |
| 四项 | 宝箱 x/4、隐藏房间 x/5、隐藏 Boss x/1、事件 x/2（与 HUD 同一份 `DungeonService.progress`） |
| 楼层 | 每层房间数、有敌人的房间数、已清数；**已通关的层**旁边就是「扫荡（仅掉落）」按钮，没通关的层写清还差哪些房间并置灰 |

扫荡按钮不自己动手：它调小地图控制器传进来的 `sweep_handler`（走 `sweep_floor`），
这样会话状态、玩家位置与掉落入包仍在控制层一处处理。快捷键 `J` 也还在（等价于扫可扫的第一层）。

顺带修掉一个真问题：**背包满时 `BattleReward.grant` 把整场结算判成失败**（掉落直接丢、扫荡报错）。
现在满仓的掉落记进 `applied.overflow`（「背包满，没捡起：草药×5」），经验与铜钱照常入账，
战斗结算与扫荡摘要都会写明——是「没捡起来」，不是「白打一场」。

### 线索本

设计 03 有一条硬要求：「线索必须能被找到，否则就是猜谜。每条隐藏至少给两个线索来源」。
`hidden_trigger.clue_source` 与 `event_check.clue_source`（分号分隔）以前**只是表里的文字**，
玩家在游戏里看不到——现在按 `K` 打开线索本（`src/core/clue_service.gd` + `scenes/clue_screen.tscn`）：

| 作用域 | 内容 |
|---|---|
| 小地图（副本/城镇里按 K） | 本图的隐藏内容（6 条）与事件判定（4 条）：名称、线索来源、表里的 `note`（这是什么）、**完成状态** |
| 大地图（按 K） | 野外事件按地标分组（落雁坡 3／荒村 1／塌陷山洞 1／黑风寨 2／清风驿 1） |

完成状态直接读存档：隐藏看 `dungeon_records.triggers`，事件看 `event_checks`（含「失败过」）；
还没做的条目（只剩 `sequence` 三火盆缺位点）会写明「这一类还缺地图位点，暂时做不了」，
而不是静悄悄消失。事件条目还会写清判定条件（`奇门 ≥ 3`、失败会怎样）。

### 潜行

设计 02 写「按住潜行键进入潜行状态（移速降至 60%，**被发现判定降低**）」，
其中「被发现判定」以前没接（`combat_const.sneak_detect_reduce = 0.4` 零引用），潜行只影响移速。现在：

| 内容 | 约定 |
|---|---|
| 移速 | 玩家控制器里已有：潜行 60%（`PlayerController.SNEAK_RATIO`） |
| 被发现判定 | 追击型明雷的**有效警戒半径** ×`(1 − 0.4)`；值从 `combat_const` 读，由控制层注入明雷（明雷本身不碰表库） |
| 潜行失败 | 被发现后 `chasing = true`，照常进入追击流程（设计原话）——不是「潜行就绝对安全」 |
| 提示 | 潜行状态变化时状态栏写一句「潜行中：移速 60%，被发现判定 ×0.60」，免得玩家不知道 Shift 有没有用 |

顺带把副本里的 **`behavior` 类隐藏触发（潜行入寨）** 接上：被任何一个房间的守卫撞上就把本次进图的
`stealth_broken` 记下来，`flag_stealth_full=1` 只认「一次都没被撞上」；被撞过就提示
「潜行已经失败过（出去再进来重新潜）」。七类隐藏触发**代码侧全部实现**（`sequence` 三火盆见决策 215；只差地编摆三个编号位点）。

### 招式冷却

`skill_active.cooldown` 有 20 个招式配了 2~5 回合，但**以前完全没用**——可以每回合连放同一招。
现在：

| 内容 | 约定 |
|---|---|
| 语义 | 冷却 N = **放完之后接下来 N 个回合不能再用**（第 N+1 个回合起可用） |
| 判定 | 按「单位 + 招式」记在模拟器里（`_cooldowns`），`available_skills`／`pick_skill` 都会过滤 |
| 界面 | 冷却中的招式仍然列出来，**灰着**并写清「冷却中（第 4 回合起可用）」——不写原因的话玩家会以为招式丢了 |
| 体检表 | `sim.skill_options(actor)` 一次给出「能不能放、为什么不能」（冷却／内力／武器／伤害类型不支持） |

这条口径（N 还是 N+1）设计没写明，按「接下来 N 回合不能放」实现，已记进对接表等确认。

### 事件判定（非战斗技能）

`event_check.csv` 里 12 条判定以前一条都没接（面板上能看到判定值，但没有任何地方用它）。
现在走 `src/core/event_check_service.gd`：

| 内容 | 约定 |
|---|---|
| 判定值 | `attr:x` 取**裸属性**（模板 + 加点，不含装备）；`skill:y` = 技能等级 + `floor(相关裸属性/5)` |
| 成败 | 判定值 ≥ `difficulty` 即成功——**没有随机**，加点与技能等级说了算 |
| 谁上 | 队伍里判定值最高的那个人（当前只有一名角色，等价于他本人） |
| 奖励 | `item` 进背包；`room` 指向某处（顺带把对应的**大地图地标揭开**，例：追足迹 → 塌陷山洞出现在地图上）；`event` 记剧情旗标；`none` 只提示 |
| 失败 | 如实转述表里的 `fail_note`（`hard` 的代价如「落石损失气血」「被发现」依赖还没做的战斗外气血／潜行状态机，所以**不假装扣血**，只记 `failed`） |
| 判重 | `once_only=1` 的成功记录（`done`）挡住重复触发；失败可以再试 |
| 存档 | `event_checks`（done/failed）+ `flags`（剧情旗标），v9 起 |

入口：小地图里 `Markers/<room>/Event_<check_id>`（4 条：柴房机关、救治囚犯、辨认毒酒、解题字）、
大地图 `Markers/Event_<check_id>`（7 条：翻墙、推门、追足迹、救治采药人、劝退强盗、读碑文、寒夜守夜），
都是走过去按 E —— 判定结果直接写在状态栏上（例：`翻越寨墙：敏 9 ≥ 9，成功`）。

### 经验与升级

**这块以前是死的**：`level_growth.csv` 有 20 级经验表，但没有任何代码消费经验——
角色永远停在 1 级、只有开局的 3 点可加，升级带来的基础属性成长也拿不到。现在接上了
（`src/core/level_service.gd`）：

| 内容 | 约定 |
|---|---|
| 升级门槛 | `level_growth.exp_to_next` 是**升下一级所需经验**（不是累计值），满级那行是 0 |
| 升级得点 | `upgrade_points`（当前每级 3 点），累计由 `GameState.available_points` 算 |
| 基础成长 | `level_growth.base_*` 由 `AttributeCalculator` 的第 3 层自动跟上（升级即变强） |
| 结算时机 | 战斗入账（`BattleReward.grant`）加完经验**当场**升级，结算面板写一行「升级：… Lv1 → Lv2（+3 点）」 |
| 跨级 | 经验够就连升（例：760 → 一口气 1 级到 4 级），池子余量留着 |
| 满级 | 20 级封顶，经验继续记账但不再消耗（面板显示「已满级」） |

**自己定的口径**（设计只写了「升级受经验限制」，没写分配规则）：经验进**队伍池**
（存档 `party_exp`），谁升级就扣一份，多人时先补等级最低的那个。等队伍扩到 3–4 人、
或设计给出分配规则时，改 `LevelService.apply_available_levels` 一处即可。

角色面板顶部会写「队伍经验 36（下一级还需 64）」，一眼能看出还差多少。

### 大地图：揭雾与驿站

设计 02 说「玩家的地图是自己走出来的」、03 说「难度可在大地图任意驿站切换」，
两条都在 `src/core/world_map_service.gd` 里按 `map_region.csv` 驱动：

| 内容 | 出处 | 约定 |
|---|---|---|
| 一开始就亮 | `reveal_on_map=1` | 清风驿／驿站／落雁坡三个（进游戏就能看见） |
| 走进才亮 | `unlock_condition=proximity_N` | 玩家进到 N 格（32px/格）内自动揭开，HUD 会提示「揭开新区域：…」 |
| 发现前置 | `unlock_condition=discover_X` | X 揭开后跟着揭开，**同一次刷新里做链式传播**（黑风寨靠 `discover_luoyanpo`） |
| 存档 | `GameState.revealed_nodes` | 揭开是永久的（v8 起），重进游戏地图不会变回全黑 |
| 驿站传送 | `node_type=fast_travel` + 按 E | 目的地只列**已揭开且有 `enter_scene`** 的节点；野外区域（落雁坡）不是目的地 |
| 难度切换 | `difficulty_config.unlock_condition` | 普通默认解锁、困难要击败大寨主、绝境还要加上醉刀客（见下） |

**两处表里没有 id 的地方，这里定死**（已记进对接表）：

1. `discover_X` 里的 X **没带 `n_` 前缀**（表里写 `discover_luoyanpo`，节点 id 是 `n_luoyanpo`），
   所以 `discovery_target_revealed()` 两种写法都认。
2. 难度解锁条件是**中文短语**（「通关第一章」「通关第一章并击败醉刀客」），
   代码里用短语当键映射到「要击败哪些敌人」，表里出现没登记过的短语会 `push_error` 并按未解锁处理
   （改文案时能立刻发现）。「第一章节」的 Boss 记录读 `dungeon_records.bosses`。

入口：大地图上走到驿站（`Markers/Node_n_post_station`）旁边按 E，面板里既能传送也能改难度；
第二行 HUD 常驻显示 `地图 3/7（未探索：黑风寨、塌陷山洞…）`。

### 多段攻击与目标类型

`skill_active` 里有「攻击段数」与「目标类型」两列，之前只用于面板显示，**结算完全没用**——
横扫（3 段·全体）当时只打单体一下、夜雨（2 段）只算一段。现在两条都接进战斗：

| 内容 | 约定 |
|---|---|
| 多段 | 每段各掷一次命中／暴击／格挡，伤害与破架势逐段结算；**目标倒下就不再补刀** |
| 破架势与异常 | 按段各结算一次（表里没写，按「每段都是一次完整命中」处理，已记在对接表等设计确认） |
| 全体 | `target_type=all_enemy` 打全场；手选招式也一样（以前只有自动战斗会展开成全体） |
| 表现 | 每段一个跳字并**按段序号错开位置**（不然数字叠在一起），日志里一次行动写一行「共 X（3 段）」 |
| 自动策略 | 按「倍率 × 段数 × 人数」排序（`_skill_score`）——只看单发倍率的话，横扫这种全体多段招永远不会被 AI 选中 |
| 未实现 | `target_type=self` 的自我强化招式（如醉步）没有 buff 系统，选招时会跳过 |

**一处口径要请设计确认**：`power_ratio` 我按**每段**理解（横扫 1.3 × 3 段 = 合计 3.9 倍），
所以横扫（3 段）现在比斩风（2.1 单体）更受 AI 青睐，单挑也照用。若设计的意思是「整招合计倍率」，
改 `_resolve_one_hit` 里的入参一处即可（把倍率除以段数）。

顺手修掉一个语义问题：`act()` 在**没有回合进行中**被调用时（用例或脚本直接出招）也会触发回合末结算，
把刚打出来的破绽窗口和架势回复一起跑掉。现在只有「本来就在回合里」才结算回合末。

阵亡表现：卡片压暗到 45% 透明度、名字标「（倒）」、并带一点倒下的位移。

### 副本完成度与扫荡

完成度与「已通关层」都是**永久记录**（存档 `dungeon_records`）——小地图的会话状态回大地图就整片刷新，
但完成度是给全清玩家的追求目标，不能跟着清。数据全部从两张表算出来（`src/core/dungeon_service.gd`）：

| 完成度项 | 出处 | 口径 |
|---|---|---|
| 宝箱开启数／总数 | `dungeon_room.chest_id` 非空的房间 | 记录键 = `房间|掉落组`（同一个掉落组可能被两个房间各放一个宝箱，只按掉落组会串味） |
| 隐藏房间进入数／总数 | `dungeon_room.branch_group = hidden` | 表里**没有** `room_type=hidden`，隐藏房间就是这个分组；玩家所在房间按 `Rooms/<room_id>/bounds` 的矩形判位置 |
| 隐藏 Boss 是否击败 | `enemy_base.threat_tag = purple` 且不在 boss 房间队伍里 | 大寨主（boss 房间）算章节 Boss，醉刀客算隐藏 Boss |
| 事件是否触发 | `hidden_trigger.reward_type = event` | 记录玩家用过的触发点 |

存档里另一种记录是 `rooms`（打过的房间），它同时决定**扫荡**能不能开：`floors()` 把房间按 `floor` 分组，
某层**所有带敌人的房间都打过**才算「已通关层」。扫荡按设计**只结算掉落、不给经验**，
可以反复扫（刷子循环的效率口）；保底计数在扫荡时也会读存档、写回存档。

入口：副本里 HUD 第二行常驻显示完成度，全清到「可扫荡」时会变成
`…　｜　可扫荡：第 1 层（按 J）`；`M` 键把完整完成度打进状态栏。

### 异常状态与持续伤害

四类 DoT（中毒／灼伤／流血／内伤）按 04_战斗与伤害.md 的规则落地，数值全在
`status_effect.csv` + `damage_type.csv` + `combat_const.csv`：

| 规则 | 实现位置 |
|---|---|
| 同源同类叠层、刷新时长（不同来源独立计算） | `BattleActor.add_status()`：键 = `status_id + source_id`，到 `max_stack` 只刷新 `remaining` |
| 每层伤害**施加时锁定**（快照制） | 每层单独存一个伤害数字，之后即使增益掉光也照原值跳 |
| 回合末统一结算 | `BattleSimulator._tick_statuses()`（回合末跳字，不按行动条各自计时） |
| 不吃暴击与格挡（流血可闪避） | DoT 走 `DamageResolver.resolve_dot()`，只看 `damage_type.can_dodge` |
| 防御口径 | 毒／灼伤／内伤无视防御，流血吃外功防御，内伤吃内功防御（`damage_type.use_def_*`）。**按状态自己的伤害类型算，不是挂它的那招**：五毒散手是直伤招式，但它挂的中毒层照样无视外功防御 |
| 敌人抗性 | `enemy_base.res_poison/res_burn/res_bleed/res_internal`（毒手 50% 毒抗、大寨主与醉刀客 20~30%）→ 抗性 `(1−x)` 压**上状态几率**；`res_internal` 另外减免**内伤类持续伤害** |
| 灼伤削防 | 每层 −5% 外功防御（`BattleActor.defense_multiplier`） |
| 内伤压制内力 | 内力回复减半（`BattleActor.qi_regen_factor`），且 `dispellable=0` 驱散不掉 |
| 斩杀补偿 | 血量低于 `combat_const.dot_execute_threshold`（15%）时剩余层数立即结算并清空 |
| 触发几率／强度 | 几率 = `base_chance × skill_active.status_chance_mul + debuff_chance(运)`，夹 0~95%；强度乘 `(1 + debuff_power(智))` |

**两处自己定的口径**（表里没给公式，已写进对接表等设计确认）：
1. 几率用**加法**把 `debuff_chance` 加在表值上（不是乘法）——两者都是概率，加法更好读；
   敌方抗性读 `enemy_base` 的 `res_poison`／`res_burn`／`res_bleed`／`res_internal`
   （毒手 50% 毒抗、大寨主与醉刀客 20~30% 三抗），抗性作为 `(1 − 抗性)` 乘数**只压几率**；
   其中 `res_internal` 还额外减免**内伤类持续伤害**（01 文档写「抵抗内伤类效果」，04 没写它落在第几步，按伤害减免乘区实现）。
2. 灼伤「每层 5%」与内伤「回复减半」只在 `desc` 文字里，代码写成常量
   （`BURN_DEF_DOWN_PER_STACK` / `INTERNAL_QI_REGEN_FACTOR`），等设计补数值列。

表现：战斗卡片上有状态行（`Status_<actor_id>`，颜色取 `damage_type.display_color`），
持续伤害的跳字也用同一颜色（中毒绿／灼伤橙／流血红／内伤紫），和直伤一眼分得开。

击杀方式会记进 `GameSession.last_battle.kill_styles`，隐藏内容用它判「毒杀」
（`hidden_trigger.required_condition = kill_with=poison`）。

### 熟练度（修炼）

每部武学独立熟练度 0 → 10（`growth_const.mastery_max`），直接乘在伤害管线第 1 步
（`招式实际倍率 = 基础倍率 × (1 + 熟练度 × 星级 mastery_gain)`）。三种来源里已实现两种：

| 来源 | 出处 | 约定 |
|---|---|---|
| 战斗中施放 | `growth_const.mastery_combat_gain`（表里注释：每次施放 +1） | `BattleSimulator` 记下谁施放了哪些招式，战斗结算时写回存档并播报「熟练度：…」 |
| 打坐修炼 | `skill_star_def.cultivate_cost_base` × `cultivate_cost_growth^(熟练度-1)` | 客栈（清风驿 `facility_inn`）按 E 打开界面；**一次打坐 = 熟练度 +1**，费用按「当前等级 → 下一级」；未学／练满／缺钱都置灰并写原因 |
| 秘籍灌注 | — | **未做**：设计只写「一次性、稀有材料」，没给材料与幅度 |

**一处需要设计确认的平衡**：`mastery_combat_gain = 1`（每次施放 +1）配上 0~10 的熟练度，
意味着一场架就能把一部武学从 0 练到 10（战斗自检里就是「玄微剑法·起手 9/10（+9）」），
打坐（花铜钱）会显得多余。这条**按表实现**，没有自己改数值，已记进对接表等设计定。

### 商店与经济

清风驿（`scene_qingfengyi`）里走到 `Markers/Buildings/<building_id>` 旁边按 E 进店，
界面盖在当前场景上（**不切场景**，所以玩家位置与「已清怪／已开箱」的会话状态都不丢；Esc 或「离开」出来）。

| 内容 | 出处 | 约定 |
|---|---|---|
| 卖什么／什么价／限不限量 | `shop_stock.csv` | 按 `building_def.stock_group` 取货架，按 `sort_order` 排；`stock_limit=0` 表示无限量 |
| 买入 | `buy_price` | 扣铜钱 → 道具进堆叠、装备进实例（**店里卖的是白板，不带词条**） |
| 卖出 | `sell_price` | 价格差就是交易税；钥匙道具、身上穿着的、>1 件的装备都不能卖 |
| 回购 | 存档 `shop_state` | **回购＝撤销卖出**：价格就是当初的卖出价，上限 20 条，满了挤掉最早的；装备连词条一起原样回来 |
| 累计买入次数 | 存档 `shop_state` | 限量商品的剩余量 = `stock_limit − 累计买入次数` |
| 治疗 | `building_def.service_id=heal` | 费用 = 缺失气血 × `service_price`（当前每点 2 文） |

**两条自己定的口径**（设计没写，写在这里免得以后猜，也已记进对接表）：

1. **只收店里有 `sell_price` 的东西**——掉落装备如果这家店没上架，它就不收。
   设计没给「估价回收」的公式，不自己编一个数值。
2. **医馆治疗只算得出价钱**：存档里没有战斗外气血（队伍每次战斗按 `character_base` 重建满血），
   所以界面把单价与公式写清楚、按钮置灰并说明原因，等设计定下「战斗外血量」再开。

自检：`-- --shop-selftest`（切四个页签 → 买白板剑 → 卖回去 → 回购 → 治疗页），
另外 `tests/test_local_map.gd` 会真的走到铁匠铺位点按 E，确认开店与关店。

城镇里还有三类**非店铺设施**（`Markers/Facilities/`，按 E 交互）：

| 设施 | 现状 | 说明 |
|---|---|---|
| 客栈 `facility_inn` | 打坐界面 | 花铜钱练熟练度 +1，公式见「成长」段 |
| 当铺 `facility_pawnshop` | 信息点 | 07 文档写它是「无表（对话线索）」：老板提到「寨里关着个疯子」（醉刀客的线索来源之一） |

### 武学：学 → 装配 → 战斗

武学是**两套独立槽位**（招式是个数、内功是容量点），规则与数值出处见 `01_角色系统.md`：

| 内容 | 约定 |
|---|---|
| 已学 | 每人一份 `char_learned`；图鉴计数 = 全队去重后的部数（`GameState.collected_skill_count`） |
| 招式槽 | `2 + 等级/5 + 悟性/8`（上限 9），装满再装会被拒并说明「招式槽已满（3/3）」 |
| 内功容量 | `2 + 等级/6 + 根骨/10`（上限 7）；每部内功按星级占 1~3 格（`skill_passive.slot_cost`） |
| 修习门槛 | `skill_base.learn_req_attr ≥ learn_req_value`（行里没写值就取 `skill_star_def.learn_req_value`）；不够就学不会，并写清「悟性需 12（当前 10）」 |
| 武器绑定 | 招式绑定武器类型（`any`／留空 = 通用）；装配时按**身上那把武器**校验，与战斗里的选招同一口径 |
| 战斗联动 | `PartyBuilder` 把装配的招式当成 `actor.skills`；内功加成走 `AttributeCalculator` 的贡献通道（装备即生效） |
| 面板 | 角色页顶部「武学（招式 1/3　内功 1/2 格）」，每行一个「装配／卸下」按钮，装不上的置灰并写出原因 |
| 学习来源 | 已做三类（都按 `skill_base.source_type` + `source_id` 配表驱动，全在 `SkillGrant`）：`drop` 击败指名敌人、`hidden` 触发指名隐藏点位、`item` 研读指名秘籍。门槛不够只在结算／触发／研读结果里说明，**不写进已学**；秘籍门槛不够时**不消耗**（别浪费稀有残页） |
| 未接来源 | `npc`（门派对话传授）、`story`（章节节点）、`shop`（商店买武学）——分别等 NPC 对话、剧情旗标、商店上架武学；`shop_stock` 目前只上架物品与装备 |

入口在哪：战斗结算播报「领悟：…」（`battle_screen._settle`）；隐藏点位在 `local_map_controller._activate_trigger`
成功后追加同一条汇总；秘籍在角色界面·背包页的「研读」按钮（`skillbook` 类道具，

## 界面骨架与版式预算

战斗界面（`scenes/battle_screen.tscn`）已经改成**真实节点树**：版式、标题、日志框、招式行、
五个按钮都在场景里，编辑器与 Godot MCP 能直接开它调位置；`src/ui/battle_screen.gd` 的 `_bind_ui()`
只做「查找节点 + 接信号」，缺节点会 `push_error` 报警而不是界面上静悄悄少一块。

节点名是接口，改名前先看这两个用例：

| 路径 | 谁在用 |
|---|---|
| `Margin/Column/Headline`、`Margin/Column/Buttons/*` | `tests/test_battle_ui.gd`、`tests/test_overworld.gd` 按名字找节点 |
| `Margin/Column/Log` | 战斗日志（`RichTextLabel`，**自带滚动 + `scroll_following`**） |
| `Margin/Column/Front/TeamAllies/AllyScroll/ListAllies` | `_refresh()` 往里塞我方卡片行 |
| `Margin/Column/Front/TeamEnemies/EnemyScroll/ListEnemies` | `_refresh()` 塞敌方卡片行，按名字找 `Actor_*`／`Name_*`／`TargetButton_*`／`Float_*` |
| `Margin/Column/SkillRow` | 按当前单位可用招式动态生成 `SkillButton_*` |

卡片行、跳字、破绽抖动是**运行时生成**的（战斗状态每回合都变），只有骨架在场景里——这条分工不要倒过来。
日志**不要**再套一层 `ScrollContainer`：`fit_content` 会让 `RichTextLabel` 撑到全高，滚动就落到外层容器上，
`scroll_following` 随之失效（打到第 9 回合日志还停在第一回合）。现在由 `RichTextLabel` 自己滚，
`--battle-selftest` 里有一条「日志跟随到底」的断言守着。

**版式预算**：整页最小高度必须塞得进设计分辨率（1152×648），否则会出现「标题被裁掉半行」或
「按钮点不到」这类看代码看不出来的问题。两侧队伍列表各留 250px 定高滚动区、日志区留 110px 可伸缩，
`--battle-selftest` 里有一条硬断言：

```
LAYOUT min_width=803 min_height=608 limit=1152x648 ok=true
LAYOUT[settled] min_width=760 min_height=637 limit=1152x648 ok=true
```

（两行分别是开战前与结算后；都是 ASCII，`findstr LAYOUT` 就能抓到。**宽度是 2026-10-03 补的**：
以前只量高度，`DESIGN_WIDTH` 声明了却没人用过——横向膨胀会被屏幕右侧裁掉而代码一声不吭。
所有面板都有这行，
见下面「版式预算推广到所有面板」。）改版式（换字号、加一行、改卡片结构）之后一定要重跑它：
这个数值曾经是 711，界面顶部直接被裁。

`tools/run_tests.bat` 一条命令跑完「生成表 → 刷新类缓存 → 自检」，退出码 0 表示全绿：

编辑器里直接 F5 会运行引导场景，控制台打印表清单、角色摘要与校验结果。

## 数据约定（与 06_配置表说明.md 一致）

- CSV 是唯一数值源，设计师只改 CSV；运行期只读生成的 `.tres`。
- 首行英文 snake_case 字段名；**带 BOM**（Excel 双击不乱码），构建脚本会剥掉。
- 比率一律小数（`0.01` 表示 1%），布尔用 `1`/`0`，空值留空。
- 引用填目标表主键 id；主键唯一非空、引用必须存在，否则构建失败。
- **公式不进表**：表只配系数、上限、曲线枚举，算法写在 `src/core/`。
- 两张表的列名与 GDScript 冲突，注册表里做了别名：`attr_to_stat.id → row_id`、`enemy_base.exp → exp_reward`。

## 大地图与战斗（最短闭环）

```
占位游戏场景 ──「进入大地图」──► world_run（大地图走动）
                                     │ 撞上明雷
                                     ▼
                              Encounter（接触规则）
                                     ▼
                        battle_screen（逐回合／自动／加速）
                                     │ 胜利：BattleReward 落账 + 明雷标已清
                                     ▼
                              回 world_run（该明雷隐藏到重生时间）
```

要点：

- **不动地编资产**：`scenes/world_run.tscn` 是壳，运行期实例化 `scenes/maps/overworld.tscn`；
  玩家与明雷挂在它的 `YSort` 下，`src/world/` 是控制层。
- **输入映射在运行期注册**（`InputSetup.ensure()`）：WASD／方向键、Shift 潜行、E 交互、Tab 角色界面、Esc 返回；
  不往 project.godot 塞 InputEvent 序列化文本，改键只改一处。
- **明雷状态是运行期的**：`GameSession.cleared_spawns[spawn_id]` 记「可重生时间」（`-1` = 不刷新），
  不进存档——与 02 文档「离开小地图回大地图整片刷新」一致。
- **接触规则**（`Encounter`）：正面按身法；背后我方先手（架势削减记暂缓）；背后沉睡=奇袭（首回合 +50%）；
  追击型进警戒圈被发现=敌方先手；被追上=敌方先手且**第一回合不能逃**（`BattleSimulator.flee_block_reason` 真判）。
  架势与拆招、逃跑都已实现，`pending_rules` 现在只剩「奇袭敌方首回合无防备」这一条等设计补列。
- **驻守／巡逻型的警戒圈只让他们转头发现你**，不额外惩罚——表里没给这条规则，按正常遭遇处理。
- **中立明雷**（采药人）贴身也不开战。
- **小地图**：`scenes/local_run.tscn` 也是壳，按 `GameSession.pending_local_scene` 加载地编场景；
  玩家从入口房间开始，房间敌人在 `Enemies/<room_id>/` 位点驻守（不追击），宝箱与触发点在 `Chest_`／`Trigger_` 位点。
  宝箱掉落走 `DropResolver` + `BattleReward` 直接进背包；隐藏触发本轮实现 `item`／`space`／`carry` 三类
  （酒葫芦触发醉刀客、铁镐挖通直通后山地牢、带锈剑进聚义厅），`sequence`／`completion`／`kill_style`／`behavior`
  因为缺位点或缺统计没有实现，交互时会直接说明原因。
- **小地图会话状态**：`GameSession.local_maps[scene_id]`（已清队伍／已开宝箱／已用触发）只在这次进出里有效，
  走 `Exit_` 回大地图就整片刷新——与 02 文档的刷新规则一致。

## 加一张新表

1. 放 `data/tables/<表名>.csv`（带 BOM，首行字段名）。
2. 写 `src/data/tables/<表名>_row.gd`，字段与列一一对应并声明类型。
3. 在 `src/data/table_registry.gd` 登记表名、行类路径、主键，必要时登记列别名。
4. 在 `src/core/table_validator.gd` 补枚举与引用规则。
5. 跑 `tools\run_tests.bat`：构建脚本会检查「CSV 列 ↔ 行类字段」是否严格对齐。

## 策划改了需求怎么办

**规则：策划增加或修改需求后，计划与验证都必须跟着改，不能只改代码。** 这条不是口头约定，
由 `tests/test_handshake.gd` 把关——没跟上就自检失败。

两份文件分工：

| 文件 | 维护方 | 作用 |
|---|---|---|
| `docs/design/CHANGELOG.md` | 设计侧 | 设计变更日志与**当前设计版本**，是所有判断的基准 |
| `docs/dev/模块对接表.csv` | 双方 | 模块 ↔ 设计文档 ↔ 配置表 ↔ 代码路径 ↔ 状态 ↔ 对齐的设计版本 |
| `docs/dev/验证清单.csv` | 开发侧 | 模块 ↔ 验证用例 ↔ **验证对齐的设计版本**，避免两边同时改对接表互相覆盖 |
| `docs/dev/设计实现对照.md` | 开发侧 | **反着查**：设计文档逐条 → 代码落点／状态，用来找「设计写了但没实现」的漏项；卡点分成「开发可做／等设计补表／等设计明确规则／等地编」 |

### API 使用审计（找「写了但游戏路径没调用」的功能）

配表审计（`tools\audit_table_usage.ps1`）只看「名字有没有出现」，**查不出「函数写好了却没人调」**——
图鉴奖励就栽在这里：`codex_bonus()` 早就写好，全项目只有用例在调，游戏里收集再多也不涨属性。
补上之后我又跑了一轮**函数级**审计，方法：对 `src/` 里每个 `func`，统计它在
① 本文件、② 其它 src／场景、③ tests 里的出现次数，按「本文件内有调用（own>1）」「别的 src 在用」
「只被测试调用」分类（排除 `_ready`／`_process` 这类引擎回调）。结果：

- **全项目一次都没被调用的死函数：0 个。**
- 只被测试调用的：22 个，逐个看过，都不是漏接的功能：查询接口（`has_status`／`has_flag`／
  `first_kill_count`／`fog_cells`…）、等数据的 helper（`is_battle_use`／`is_field_use` 等消耗品效果列；
  `clear_dispellable` 等「可驱散」的驱散来源）、以及没有 UI 需求但留着的 API
  （`delete_slot`——设计文档里没有「删除存档」这一条）。

所以「算了但没发」这一类目前是干净的。下次再加类似功能，先问一句：**这个函数游戏路径真的调到了吗？**

标准动作：

1. 读 `CHANGELOG.md`，确认当前设计版本与受影响模块。
2. 在对接表里找到自己的模块，判断改的是数值、公式还是行为。
3. 改配置表与代码。
4. **补或改用例**：新增能力要有新断言；数值变了要把受影响的黄金值、区间、边界一起更新；
   行为被删掉要把原来的断言删干净（别留“永远真”的空验证）。
5. 回填 `验证清单.csv` 的 `verify_paths` 与 `verified_design_version`，同步对接表的 `design_version` 与 `status`。
6. 跑两条校验：

```bat
tools\run_tests.bat
powershell -NoProfile -ExecutionPolicy Bypass -File tools\validate_tables.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File tools\audit_table_usage.ps1
tools\run_all_checks.bat
```

**最后那条是给交接用的唯一验收命令**：它把上面的检查、**地图验收**、**跨场景闭环**与
10 个真实场景自检串起来，逐步打印 `[OK]/[FAIL]`、末尾汇总，退出码 0 = 全绿
（**步数以运行输出的 `passed steps: N` 为准**——这里不写死）。结构（都是纯 ASCII + CRLF）：

| 文件 | 作用 |
|---|---|
| `tools\run_all_checks.bat` | 编排：逐条调用下面两个子脚本，`&&`/`||` 当场判定 OK/FAIL 并累计 |
| `tools\check_command.bat` | 跑一条普通命令（自检 / 表校验 / 配表审计），把退出码原样传回 |
| `tools\check_scene.bat` | 跑一个场景自检：起引擎、按 `SELF-TEST: OK` 标记判定、把判定行与 `LAYOUT` / `BACKDROP` 契约行一起打出来 |
| `tools\check_maps.bat` | 跑**地图验收**（`tools\mapgen\verify_maps.gd`，即 07 第九节那 6 条：命名归属／连通性／可绕背袭／侧向通路／巡逻／性能），按 `MAPCHECK: OK` 判定，附每张图的计数行 |
| `tools\check_loop.bat` | 跑**跨场景闭环 + 整局巡游**（`tools\check_loop.gd`）共 **12 段**（段数=代码里的段标记；运行时打印十几行 `LOOP` 证据，一段可能两行）：大地图→小地图、小地图→回大地图（且不被立刻送回）、明雷战斗→回大地图（按结局分支）、驿站传送→进图→回图、房间战斗→回小地图、**副本巡游（开箱→完成度→可扫荡）**、存档→读档指纹比对、**主菜单新建游戏→小镇（进店／打坐／手动存档读档／赌局位点）**、**隐藏 Boss 交接（酒葫芦→醉刀客→回图→记成 Boss）**；按 `LOOPCHECK: OK` 判定 |
| （`run_all_checks.bat` 最后一步） | 查「跑完有没有留下引擎进程」：用 `Get-Process` 查，查到列 PID 判红，**查不动也判红** |

汇总里有 `passed steps: N` 与 `PERF total_elapsed_ms=…` 两行。**步数与耗时都以运行输出为准**
（**步数以运行输出的 `passed steps: N` 为准**，这里不写死；耗时看 `PERF total_elapsed_ms`，当前约 30 秒）
——docs 里不再写死步数，免得加一步就漏改一处（真漏过一次：
接进 `check_loop` 之后这里还写着「15 步」）。**`PERF` 只是给人看的趋势数，不是门限**：
绝对耗时依赖机器，定门限只会把噪声变成假红；真要查某一步变慢，看 `.logs\<name>_stdout.log`。

两个坑都写进脚本注释了：① 在本脚本里写 `call :label` 会报「找不到批处理标签」（cmd 怪癖），所以拆成子脚本；
② 场景自检必须带 `--quit-after 900` 兜底——自检开关写错时场景不会跑自检也不会退出，会把验收挂死
（真挂过一次）；现在它会自己退出、因为缺 `SELF-TEST: OK` 而判红，而且后面的步骤照跑。
这条链做过**反向验证**：把 battle 那步的开关改成假值 → `[FAIL] scene:battle`、`passed 12`、
`FAILED steps: battle`、`ALL CHECKS: FAILED`、退出码 1，其余 12 步照常跑完。
最后那步「不许留下引擎进程」也单独验过两条：真有残留 → `[FAIL] engine process still running (PIDs: 26868)` +
退出码 1；把查询改成故意抛错 → `[FAIL] could not query the process list -- cannot prove no engine was left behind`。
这两条不是假想：**搭这套脚本时真漏过两次进程**（一次是自检开关写错挂死，一次是早先的残留），
而且第一版用 `tasklist` 查——它在当前会话里直接 `Access denied`，于是检查**静默通过**成了假阴性，
改成 `Get-Process` 后把「查不动」也算失败。

第三条是**配表使用审计**：查「配了但 `src/` 里一个字都没提」的列与常数（筛子，不是证明——
它只看名字有没有出现，读得对不对靠用例）。当前 37 张表 0 个死列、`combat_const`＋`growth_const` 23 个常数 0 个没人用。
（顺带一句坑：带中文的 `.ps1` 必须存成 UTF-8 **带 BOM**，否则 PowerShell 5.1 按 ANSI 读会连语法都报错。）

自检会拦住八类问题：已动工模块的设计版本落后于 CHANGELOG、已动工模块没登记验证用例、
验证用例文件不存在（改名忘了同步）、`tests/` 里出现没人引用的孤儿用例、
对接表的 `code_paths`／`data_tables`／`design_docs` 指向不存在的东西、
`docs/design/` 下出现没人引用的设计文档、**`src/` 下出现没人引用的脚本**、**`scenes/` 下出现没人引用的场景**。

后两类是「反查对接表自己」：那三列是写给设计侧「去哪找」的，写错了比不写更糟；
一篇没人引用的设计文档则等于「没人负责的设计」。两条都做过反向验证——
把 `drop_system` 的 `code_paths` 改成不存在的文件名 → 报
`drop_system 的 code_paths 引用了不存在的文件：src/core/drop_resolver_TYPO.gd`；
往 `docs/design/` 里丢一篇没登记文档 → 报 `设计文档 99_临时孤儿.md 没有被任何模块的 design_docs 引用`。

最后两类是「死代码检查」：判定被引用的方式是**路径字符串出现在别处**（`preload`／`load`／场景的
`ext_resource`／autoload 配置）或**它的 `class_name` 在别的文件里被用到**。当前 91 个脚本 + 18 个场景
全部有引用；反向验证是往 `src/core/` 与 `scenes/` 各丢一个没人引用的探针 →
`孤儿脚本：src/core/__orphan_probe.gd` 与 `孤儿场景：scenes/__orphan_probe.tscn` 双双报红（探针已删）。
真要留一个「暂时没人用」的东西，加进 `test_handshake.gd` 的 `INFRASTRUCTURE_SCRIPTS` 并写明理由。

如果策划改的是已经实现的部分（比如调整了伤害公式的系数），即使代码不用动，也要在用例里体现：
新增一条钉住新数值的断言，或更新原有的黄金数值，并把 `verified_design_version` 推到新版本——
「需求变了但验证没变」本身就是缺陷。
