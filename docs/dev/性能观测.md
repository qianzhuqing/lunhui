# 性能观测（体量快照）

> **这是什么**：把「人最多 / 列表最长 / 存档最满」的几组极端数据跑一遍，看现在要花多少时间、占多少内存。
> **不是**验收门限——耗时随机器与当时负载波动，做成门限只会让正常波动变成假红。
> 与 `平衡观测.md` 同一类：**只描述现状**，人工整理回本页。
> **快照日期**：2026-10-04（设计版本 **0.31.0**；§二 那张表是 0.6.1 的老口径，**最新一次见「三之四」**）。
> 0.7.0（buff／套装）与 0.8.1（六指令／战败处理）各重测过一次，2026-10-04 又重测了一次（三之四）。
> **代码或数据一改，本页就过期**：重跑下面那条命令，把新数字贴回来即可。
>
> **读的时候注意**：§二 的数字来自**44 张表 / 675 行**那一版数据，现在是 **64 张 / 1023 行**——
> 所以"构造夹具"这一项从 1.6 ms 涨到 7.6 ms 是**夹具要复制的行变多了**，不是引擎路径变慢
> （同一节里那句解释现在依然成立）。**要对照就看三之四。**

## 一、怎么复现

```bat
tools\run_perf_analysis.bat
```

只读分析：不改数值、不写存档，约 1 秒，把原始数字打在控制台（也落在 `.logs\perf.log`）。
脚本：`tools/analysis_perf.gd`（与 `analysis_balance.gd` 同一套骨架：`extends SceneTree` + `--quit-after` 兜底）。

## 二、口径

| 项 | 取值 |
|---|---|
| 机器 | 本机（Windows，headless，Godot 4.7.1 stable console） |
| 计时 | `Time.get_ticks_usec()` 差值；**每项在同一会话里连测 3 次，报中位数并打印最小–最大**（2026-10-03 改，见 三之二）。单次数字分不清冷启动与稳态——实测「线索本查询」第一次 4.8ms、后两次 0.2ms，单跑一次抽到哪个全看运气 |
| 内存 | `Performance.get_monitor(Performance.MEMORY_STATIC)`——进程级（含引擎本身），只作量级参考 |
| ① 满配队伍 | 4 人（复制模板行）＋每人 6 件实例（含武器/戒指/头/身/饰品/腰带）＋大背包（15 种道具各堆满） |
| ② 长线索列表 | 黑风寨隐藏内容复制 6 倍 → 36 条隐藏 ＋ 4 条事件 = 40 条 |
| ③ 多层副本 | 黑风寨第 1 层房间复制成 30 层 |

## 三、观测结果（2026-10-03）

| 场景 | 数字 |
|---|---|
| 4 人满装 + 大背包：构造 | 1.6 ms |
| 同上：造战斗单位（含装备贡献） | 1.4 ms（4 人） |
| 同上：4v4 完整模拟（绝境黑风精英） | 4.1 ms（enemy 胜，8 回合） |
| 同上：存档序列化 | 0.2 ms（5.0 KB） |
| 同上：读档 | 0.4 ms |
| 线索本 40 条：查询 | 4.9 ms |
| 线索本 40 条：开面板并建 40 行 | 1.3 ms |
| 完成度 30 层：取完成度 + 分层 | 6.0 ms |
| 完成度 30 层：开面板并建 30 行 | 8.3 ms |
| 静态内存（进程级） | 62.8 MB |

### 三之一、0.8.1 重测（2026-10-03 深夜：buff 结算／六指令／战败处理／战斗外增益接上之后）

重跑 `tools\run_perf_analysis.bat`，同样的口径、同一台机器：

| 场景 | 0.6.1 那次 | 0.8.1 这次 | 怎么看 |
|---|---|---|---|
| 构造 | 1.6 ms | 5.3–5.6 ms | **不是游戏路径**：这一段量的是**测试夹具**（`table_with_n_chars(4)` 复制整张表 + 建 1 局），
0.7.0 加了 7 张新表（44 张 / 675 行）之后夹具要复制的行变多；拆开量过：复制表 4.1 ms、new_game 0.9 ms、
装备 24 件 0.35 ms——引擎里的装备／道具路径本身没变慢 |
| 造战斗单位 | 1.4 ms | 3.7–4.2 ms | 单次冷启动量（同一个进程里第一次 `PartyBuilder` 会顺带加载 buff／套装／贡献那几个脚本）。
稳态另有实测：`Inventory.contributions_for` 4 人合计 **0.8 ms**、`CharacterSheet.stats()` 4 人 **2.9 ms** |
| 线索本 40 条：查询 | 4.9 ms | 4.9 ms | 一致 |
| 完成度 30 层：取完成度 + 分层 | 6.0 ms | 5.9 ms | 一致 |
| 完成度 30 层：开面板并建 30 行 | 8.3 ms | 8.5 ms | 一致 |
| 4v4 完整模拟 | 4.1 ms | 4.2–4.3 ms | 一致（buff 结算只在变化时重算属性，不是每帧） |
| 静态内存（进程级） | 62.8 MB | 63.9 MB | 量级一致 |

**这一节的意义**是把「哪一段变慢是游戏代码、哪一段是夹具／冷启动」分开说清楚：
buff 结算那批改动**没有**给游戏路径带来可感知的开销（最重的单步仍然是建几十行 Control 的极端夹具）。
顺带做了一处真实优化：`BuffService` 现在把 `buff_grant` 按来源分桶、把 `buff_stat` 结果按 buff 缓存
（表在运行期只读），`contributions_for` 每次调用只建一个服务实例——见 `框架说明.md` 决策 213。

### 三之三、2026-10-03 深夜（0.13.0）：**夹具口径修正 + 重测**

这一轮重跑时先发现**夹具坏了**：`analysis_perf.gd` 的「4 人满装」是 `table_with_n_chars(4)` +
GameState.new_game(wide) 造出来的，而 0.10.0 起 
ew_game() 只给 
ecruit_def.is_initial 的成员
（开局书生一人）——于是这段**静默退化成「1 人满装」**，打印里出现「（1 人）」、4v4 模拟 1 回合就结束。
量到的已经不是本页要测的最重夹具（同族问题见框架说明决策 161：夹具跟着设计状态漂移）。

修法：改成 helper.party_state(wide, 4) —— **显式点名 4 人**（和 `tests/test_case.gd` 里
party_state 的注释同一口径）。修完重测：

| 场景 | 三之二（4 人） | 本次（4 人） |
|---|---|---|
| 4 人满装 + 大背包：构造 | 5.7ms | 6.5ms |
| 同上：造战斗单位（含装备贡献） | 4.2ms | 4.6ms |
| 同上：4v4 完整模拟（绝境黑风精英） | 7.1ms（8 回合） | 4.5ms（5 回合） |
| 同上：存档序列化 / 读档 | 0.2ms / 0.4ms（5.0 KB） | 0.2ms / 0.4ms（5.4 KB） |
| 线索本 40 条：查询 / 开面板并建 40 行 | 0.2ms / 1.3ms | 0.2ms / 1.3ms |
| 完成度 30 层：取完成度 + 分层 / 开面板并建 30 行 | 5.7ms / 8.4ms | 5.8ms / 8.3ms |
| 静态内存（进程级） | — | 64.8 MB |

战斗那一行（7.1ms／8 回合 → 4.5ms／5 回合）**不能当性能回归看**：回合数变了说明**同一场仗打出来不一样了**
（0.10.2 给角色补齐了起始装备、0.13.0 改了每级点数），本页本来就是「同一台机器上的量级参考」。
要精确对比战斗耗时就固定一份夹具快照，见决策 154 的口径。
### 三之二、2026-10-03 复测（工具改成「同会话连测 3 次取中位」之后）

`tools/analysis_perf.gd` 的口径改了：每项在同一趟里连测 3 次，**报中位数并打印最小–最大**。
理由是上面那条——单次数字分不清冷启动与稳态。同一会话里的稳定性很好（多数项落在 ±0.2ms），
但**跨会话仍能差 2–3 倍**（同一天量到的构造：5.3 / 5.5 / 5.6 / 5.7ms），所以本节的数字
**不能**与前面两次「单次（往往抽到冷启动）」逐格相比——看量级、看波动范围，别当版本间的精确回归。

| 场景 | 本次中位（最小–最大） |
|---|---|
| 4 人满装 + 大背包：构造 | 5.7ms（5.7–5.7） |
| 同上：造战斗单位（含装备贡献） | 4.2ms（4.1–4.2）（4 人） |
| 同上：4v4 完整模拟（绝境黑风精英） | 7.1ms（7.1–7.1）（enemy 胜，8 回合） |
| 同上：存档序列化 / 读档 | 0.2ms / 0.4ms（5.0 KB） |
| 线索本 40 条：查询 / 开面板并建 40 行 | 0.2ms（0.2–4.8）/ 1.3ms（1.3–1.3） |
| 完成度 30 层：取完成度 + 分层 / 开面板并建 30 行 | 5.7ms（5.6–5.8）/ 8.4ms（8.1–8.5） |
| 静态内存（进程级） | 64.2 MB |

> 两处值得写下来的读法：① 「线索本查询」的中位 0.2ms 与范围里的 4.8ms 是**同一项的三次**——
> 第一次冷启动、后两次稳态，中位取到稳态、范围把冷启动留着（这正是改成中位的意义）；
> ② 4v4 模拟这次是 **7.1ms（三次全 7.1）**，比前面记的 4.1–4.3ms 高——它不像抖动，
> 更像这台机器当前状态与当时不同（编辑器一直开着）；战斗模拟那条路径这几轮**没有代码改动**，
> 量级也仍在 10ms 以内，先如实记着，不下结论。

### 三之四、2026-10-04（0.31.0）：数据从 44/675 长到 64/1023 之后重测

这一轮没改战斗代码，但**数据长了一大截**（64 张表 / 1023 行），而且这几轮加了图标／敌人剪影／
创建界面的卡与汇总——所以把最重的那几组夹具再跑一遍（同一台机器、同一口径）：

| 场景 | 三之三（0.13.0） | 本次（0.31.0） | 怎么看 |
|---|---|---|---|
| 4 人满装 + 大背包：构造 | 6.5 ms | **7.6 ms** | 涨的是**夹具要复制的行**（44→64 张表）：这一段量的是 `table_with_n_chars(4)`（复制整张表 + 建 1 局），**不是游戏路径** |
| 同上：造战斗单位（含装备贡献） | 4.6 ms | **4.5 ms** | 一致（含天赋 `rule:` 那一份快照，仍是一次性的） |
| 同上：4v4 完整模拟（绝境黑风精英） | 4.5 ms（5 回合） | **2.5 ms（2 回合）** | **不是性能回归也不是优化**：回合数变了说明这一场打出来不一样了（敌人七维 0.28.0 重配过） |
| 同上：存档序列化 / 读档 | 0.2 / 0.4 ms（5.4 KB） | **0.2 / 0.4 ms（5.6 KB）** | 一致（多出来的 0.2 KB 是天赋／自建模板那几项） |
| 线索本 41 条：查询 / 开面板并建 41 行 | 0.2 / 1.3 ms | **0.3 / 1.4 ms** | 一致 |
| 完成度 30 层：取完成度 + 分层 / 开面板并建 30 行 | 5.8 / 8.3 ms | **5.8 / 8.3 ms** | 一致 |
| 静态内存（进程级） | 64.8 MB | **67.0 MB** | 量级一致（+2.2 MB 大致就是新表与新贴图） |

**结论**：这一轮加的图标／剪影／创建界面**没有可感知开销**；唯一明显变化的是"构造夹具"，
而那一段量的本来就是数据规模。**要拿它当版本回归对照，得先固定一份夹具快照**
（决策 154 那条口径：跨版本比"同一场仗"的耗时，得先保证打的还是同一场仗）。


## 四、看到的几件事

1. **最重的单步是「完成度面板建 30 行」8.3–8.4 ms**，其次是「4v4 模拟」（4.1–7.1 ms，跨会话有差）
   与「完成度取数」5.7 ms（**以 三之二 那次中位为准**；「线索本查询」在稳态只要 0.2 ms，
   先前那个 4.9 ms 抽到的是冷启动那一次）——
   都远低于一帧预算（60fps ≈ 16.7 ms），而且这些规模比发行数据大一个量级
   （真实只有 1 个角色、3 层、8 条线索）。
2. **存档与读档都在毫秒以下**（5 KB 的档），所以「打一场自动存档」的开销可以忽略。
3. **没有发现需要动手优化的地方**：现在的瓶颈只在「一次建几十行 Control」这种极端夹具上，
   而那种规模在第一章到不了。真要优化，优先看面板行数（完成度 30 层的 8.3 ms 里几乎全是建行）。

## 五、已知限制（这份快照没覆盖的）

- **帧内渲染**没量：headless 下没有真实绘制，跳字/动画/粒子这些表现层开销不在口径内。
- **长时间运行**没量：不测内存增长（只想看「一场/一屏」的量级）。
- **多人分支只到 4 人**（`GameState.MAX_PARTY` 上限）：设计要的 3–4 人已覆盖。
