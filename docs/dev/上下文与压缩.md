# 上下文与压缩（为什么线程会涨到 60 万 token/轮）

> 2026-10-04 实测。结论先写：**成本 = 上下文 × 工具调用次数**，涨得快的主因是
> **模型自己的思考块**（占 46%），**不是**"读了大文件"。
> 这条是根 `AGENTS.md`「主动退休」那一节的展开，判据、阈值、量法都在这里。

## 一、量法（唯一判据是「每轮 input token」）

```powershell
Get-ChildItem $env:USERPROFILE\.codex\sessions -Recurse -Filter *.jsonl |
  Sort-Object Length -Descending | Select-Object -First 8 | ForEach-Object {
    $u = (Get-Content $_.FullName -Tail 60 |
          Where-Object { $_ -match '"type":"token_usage_record"' } |
          Select-Object -Last 1 | ConvertFrom-Json).payload.usage
    "{0,9:N0} tok/轮  {1,7:N1} MB  {2}" -f $u.input_tokens, ($_.Length/1MB), $_.BaseName }
```

**别看会话文件大小**（`Length`）：2026-10-04 实测「小美术1」的会话只有 **2.0 MB**，
却在每轮发 **65.7 万** token——图多的线程字节都压在 base64 里，看大小会严重低估。

## 二、上下文是怎么长起来的

只算 `response_item`（`.jsonl` 的尺寸约是真实内容的 2 倍——`event_msg/item_completed`
会把每条内容再抄一遍，按文件大小估算是错的）：

| 线程 | 思考块 | 工具输出 | 调用参数 | 回复 | 思考占比 |
|---|---|---|---|---|---|
| 小程序（新） | 934,997 | 608,373 | 362,564 | 146,358 | **46%** |
| 小策划（新） | 458,035 | 255,548 | 134,019 | 134,832 | **47%** |
| 小地编 | 479,128 | 507,316 | 208,402 | 66,221 | 38% |

**净增长 ≈ 1,500 token × 工具调用次数。** 两个独立观测：

- 小程序 48,298 → 551,560（**+503k**），同期约 **330 次**工具调用；
- 2026-10-04 压缩后实测：35,795 → 43,580，**5 次请求涨 7,785**，即 **1,557／次**。

**与"读了什么"几乎无关**——读一份 3 万字符的文档和跑一条命令，对下一轮的影响是同一个量级，
因为**每调一次工具，整个上下文都要重发一遍**。于是线程寿命 ≈ **450 次工具调用**
（2 万 → 70 万）；小屋实测 **4.3 次/分钟 → 约 105 分钟**撞墙。

## 三、自动压缩的阈值配在哪（两个全局文件，都不在仓库里）

```
C:\Users\Administrator\.codex\config.toml
  model = "deepseek-flash"
  model_reasoning_effort          = "high"      ← 思考块占 46% 的直接来源
  model_auto_compact_token_limit  = 300000      ← 2026-10-04 18:20 加的；加了才触发

C:\Users\Administrator\.codex\cc-switch-model-catalog.json
  context_window = max_context_window = 1048576
  effective_context_window_percent    = 95      ← 95% × 1M ≈ 99.6 万
  auto_compact_token_limit            = null   ← 空，于是沿用上面那个百分比
```

**为什么以前一次都没触发过**：两处算出来的阈值都落在 **99.6 万**，而网关在 **70–90 万就拒**
（413 `Payload Too Large`）——**线程永远死在压缩之前**。2026-10-04 18:20 之前，
全库真·压缩事件（`"type":"compacted"`）= **0 条**。

同族键还有（键名已在本机 `codex.exe` 里核对过，不是猜的）：
`model_auto_compact_token_limit_scope`、`model_post_turn_compact_threshold_percent`（0–100 的百分比）、
`auto_compact_fallback_buffer_tokens`。

## 四、2026-10-04 18:23 实测：30 万生效

| 线程 | 压缩前 | 中间态 | 压缩后 |
|---|---|---|---|
| 本线程（token 优化） | 604,690 | 377,611 | **36,436** |
| 小程序 | 608,126 | 337,177 | **35,795** |

同一轮内就压完了，**线程照旧往下跑，不是开新线程**。

**怎么确认压缩真的发生过**（别 `grep compact`——它会命中聊天记录里说的"压缩"两个字，
2026-10-04 就误报过 11 条）：

```powershell
Select-String -Path <那条线程的 rollout-*.jsonl> -Pattern '"type":"compacted"'
```

`compacted` 事件里装的是**一份接手摘要**（"Another language model started to solve this
problem…"），之后的历史被摘要替换。**记住这个形状**：压缩会**丢掉思考块**，
这正是 `reasoning_text` 那条报错的温床，也说明压缩失败时的退路还是「写交接单 → 开新线程」。

## 五、阈值怎么选

| 阈值 | 两次压缩之间的工具调用 | 说明 |
|---|---|---|
| **30 万**（当前） | ≈ 170 次 | 保守；每次压缩要生成一次摘要 |
| 40 万 | ≈ 240 次 | 折中 |
| 50 万 | ≈ 300 次 | 更省，但离网关那道 70 万的墙只剩 20 万 |

**上限别碰 70 万**——那是网关按**字节**拒请求的位置；一旦撞上，之后每一轮都发不出去
（413 不会自己恢复，是唯一"重发也没用"的那种错）。

## 六、和「主动退休」那条触发线的关系（2026-10-04 起要重看）

根 `AGENTS.md` 原来写「自己这一轮 > 40 万 token，或任何一条 > 50 万」就退休。
**压缩生效后这条不会再触发**——单轮 input 到 30 万就被压回 3.6 万。
真正的判据变成：① **一轮里的工具调用次数**（成本是乘数，327 次那种仍然要禁）；
② **累计消耗**；③ 会话文件体积（413 的判据是字节，不是 token）。

## 七、降本的两个旋钮（都改全局配置，改前先问用户）

- `model_reasoning_effort = "high"` → 思考块占 **46%** 的直接来源。执行类线程（跑验收、
  改表、落文件）**不需要 high**，降到 `medium` 直接砍掉近一半增长。
- 压缩阈值本身（见第五节）。
