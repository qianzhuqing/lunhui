131. **同一个 drop_group 里 `slot` 重复 → 掉落顺序不确定**（数据不变量，今天表里没有重复，属于防回归）。
    线索：`DropResolver` 是 `rows.sort_custom(slot < slot)`——Godot 的 `sort_custom` **不稳定**，
    两个同号槽谁先谁后unspecified；而设计写的是「按 drop_group 顺序判定槽位」。
    保底计数键是 `drop_group|drop_row_id`（决策 9），**不受影响**，所以这条坏了更难发现：
    表现只是「同一颗种子的两局掉落顺序不同」。
    做法：`TableValidator._check_drop_item_refs` 里按 `drop_group|slot` 建索引，重复就报错并点名两行。
    验证：`test_table_pipeline` 补一段负向用例（把第 2 行改成与第 1 行同组同槽 → 校验必须点名）。
    断言 5664 → **5666**。**反向验证**：把这条规则关掉 → 用例立刻报
    `同一组里 slot 重复应被校验抓到`。
    数据现状核对过：现在 49 个槽没有重复（所以新规则不会把现有表判红）。

133. **`level_growth` 缺号：升级会静默卡住，经验池却一直涨**（新加一条连续性门限）。
    `LevelService` 是**按等级号直接查行**的（`db.get_row("level_growth", level)`），
    缺一行时 `exp_to_next()` 返回 0，升级循环里 `cost <= 0 → continue`——玩家卡在缺号的前一级、
    经验池只涨不升，面板上看起来只是「怎么还不升级」；`max_level()` 取的是最大编号（不是行数），
    缺号还会让它算错。
    做法：`TableValidator._check_level_growth_rows`——从 1 级起、一级一行、中间不许缺号，
    缺号时点名「缺 N 级这一行（前 → 后）」。
    验证：`test_table_pipeline` 补一段负向用例（删掉第 7 级那一行 → 校验必须报「缺 7 级」）。
    断言 5669 → **5670**。**反向验证**：把这条检查从 `validate()` 里注释掉 → 用例立刻红
    （`level_growth 缺号应被校验抓到`）。数据现状：20 行、1~20 连续，新规则不会把现有表判红。

134. **词条目标写错 → 词条「看起来有用、实际一点不加」**（`affix_pool.target` 以前没有引用校验）。
    `AffixRoller.contributions_of` 是**按前缀定层**的（`prefix == "attr"` 走属性点层、否则走固定值层），
    于是三种写法错都会静默失效：漏前缀（`str`）、前缀拼错（`attrr:str`）、目标 id 打错（`attr:strength`）——
    `AttributeCalculator` 查不到就忽略，装备描述里照样写着「力 +3」，玩家却一点属性都没涨。
    另外 `value_kind` 与目标层也要对上（`attr_point` ↔ `attr:`、`flat`/`rate` ↔ `stat:`），
    否则同一件事有两个互相矛盾的说法（运行期只看前缀）。
    做法：`TableValidator._check_affix_targets`（与早就有的 `_check_passive_stats` 对称）：
    前缀必须是 attr:/stat:、目标必须在 `attribute_def`/`stat_def` 里、`value_kind` 必须与层一致。
    验证：`test_table_pipeline` 补一段负向用例（三种错各改一条 → 正好报三条）。
    断言 5670 → **5671**。**反向验证**：把这条检查注释掉 → 用例立刻红
    （`三种词条目标错各报一条：[]（实际 0，期望 3）`）。数据现状：20 条词条，前缀只有 attr/stat、
    `value_kind` 全部对应，新规则不会把现有表判红。

136. **装备的等级需求超过上限 → 永远穿不上**（新门限，和「配了但拿不到」同类）。
    `equip_base.level_req` 以前**一条校验都没有**：设计写「需要 25 级」而等级只到 20 时，
    这件装备会在背包里一直写着「需要 25 级」，玩家满级也穿不了，而且不报错——死内容。
    做法：`TableValidator._check_equip_level_reqs` 要求 `1 ≤ level_req ≤ 等级上限`；
    等级上限抽成 `TableValidator.max_level(db)`（= `LevelService.max_level()` 的口径：`level_growth` 里最大的那一级），
    顺带把之前 `start_level` 检查里自己算的那份换成同一个函数（同一事实只留一处）。
    验证：`test_table_pipeline` 补一段负向用例（第一件装备 `level_req = 上限+5`、第二件 `= 0` →
    正好报两条）。断言 5673 → **5675**。**反向验证**：把这条检查注释掉 → 用例立刻红
    （`超上限与低于 1 级各报一条：[]（实际 0，期望 2）`）。数据现状：level_req 1~10、上限 20，不会判红。

139. **敌人表的战斗数值补上下限**（决策 129/130 那一类的第三批，这次扫到 `enemy_base`）。
    以前只有 `level ≥ 1`、`hp_base ≥ 1` 两条；攻击/防御/身法/架势**没有下限**——
    **负防御会让伤害公式反向**（`def/(def+常数)` 为负 → 减免变成加伤，
    也就是「防御越低越抗打」这种荒谬结论），负攻击则让每一击都打到伤害下限。
    比率类（命中/闪避/暴击/四种抗性）也没有上限：1.5 的命中、2.0 的闪避、1.5 的抗性都是写错，
    而运行期各有各的兜底（命中夹在 5%~99%、抗性乘算）——**看起来正常，实际不是设计要的**。
    做法：`RANGES` 里补 13 条——六个战斗数值 `min 0`、七个比率 `min 0 / max 1`。
    验证：`test_table_pipeline` 补一段负向用例（把 `def_phys` 改成 -5、`res_poison` 改成 1.5 →
    正好报两条）。断言 5689 → **5690**。**反向验证**：把这两条规则注释掉 → 用例立刻红
    （`负防御与超额抗性各报一条：[]（实际 0，期望 2）`）。数据现状全部合规（atk/def ≥ 0、
    比率都在 0~1），新规则不会把现有表判红。

140. **难度倍率必须严格为正**（`difficulty_config` 以前一条区间规则都没有）。

    0 倍经验 = 这个难度一点经验都不给；负值更不用说。运行期都不会报错，只会「安静地不对」。
    做法：五个倍率列（敌血/敌攻/敌防/经验/铜钱）加 `min 0.0001`——这是项目里

    注意下限**不是 1**：以后加「简单」难度（0.8 倍）是合法的，门限只拦 0 与负数。
    验证：`test_table_pipeline` 补一段负向用例（`enemy_hp_mul=0`、`exp_mul=-1` → 正好报两条）。
    断言 5690 → **5691**。**反向验证**：把这两条规则注释掉 → 用例立刻红

141. **两条「数据写了等于没写」的门限**（都是先量数据、确认干净之后才加的）。
    ① **非白板装备至少要有一条加成**：05 的装备阶梯是「白板 → 良品 → 珍品 → 绝品」，
    「白板」指**没有随机词条**（固定属性还是有的，店里就卖这个）；良品以上如果固定加成全是 0，
    就和白板没区别——玩家花更贵的价钱买到同一件东西。实测当前数据**没有**这种行（24 件里
    非 common 的都有加成），所以这是一条防回归的绊线。
    ② **`skill_passive_stat.value` 不能为 0**：一条写着 0 的加成是白填，装了等于没装那一部分；
    `_check_passive_stats` 以前只保证「每部内功至少一条加成」，没保证「每条都有效」。
    实测 48 条加成 0.05~80，没有 0 也没有负值（负数没拦：设计没提「副作用型内功」，
    真要加也说得通，留给设计定）。
    验证：`test_table_pipeline` 补两段负向用例（把某件非白板装备的 15 个加成列全清零 →
    校验必须报「和白板没区别」；把一条内功加成改成 0 → 必须报「白填」）。
    断言 5691 → **5694**。**反向验证**：把两条检查一起关掉 → 两条红
    （`非白板装备全零加成应被校验抓到`、`内功加成 value=0 应被校验抓到`）。

143. **加了「性能观测」这一份只读快照**（`tools/run_perf_analysis.bat` → `docs/dev/性能观测.md`）。
    起因：正确性门限已经建了一大批（决策 100–142），但**没有一处量过「极端规模要花多少」**——
    玩家侧的「卡不卡」只有肉眼印象。口径：4 人满装 + 大背包、线索本 40 条、副本 30 层，
    分别量构造/查询/开面板建行/存档往返的毫秒数与进程静态内存。
    实测（本机 headless）：4v4 模拟 **4.1 ms**、线索本 40 行 **1.3 ms**、完成度 30 层建 30 行 **8.3 ms**、
    存档 0.2 ms（5 KB）/读档 0.4 ms、静态内存 62.8 MB——都在一帧预算（16.7 ms）内，
    而且这些规模比发行数据大一个量级，**结论是目前没有需要动手优化的地方**（瓶颈在「一次建几十行 Control」）。
    与 `analysis_balance.gd` 同一套做法：`extends SceneTree`、只读、`--quit-after` 兜底、**不进验收**
    （耗时随机器波动，做成门限只会假红）。
    自己踩的两个坑记一下：① `Performance.MONITOR_MEMORY_STATIC` 在 4.7 里叫 `Performance.MEMORY_STATIC`
    （写错是解析期报错，脚本根本跑不起来）；② **`--script` 模式下 `add_child` 不会触发 `_ready`**——
    本项目的用例都显式调 `setup()`，我第一版漏了，两张面板量出来都是「0 行、0.0ms」，
    看不出是「真的快」还是「根本没建」。
    顺带把两个夹具收进 `tests/test_case.gd` 共用（`table_with_duplicated_triggers`／`table_with_many_floors`），
    用例与观测工具从此用同一份，不会各改各的。

145. **给「校验器自己的规则表」加自检——顺手发现规则写错会让整段校验中断**。
    这几十轮往 `TableValidator` 里一条条加了约百条规则（`REFERENCES`/`RANGES`/`RELATIONS`/`ENUMS`），
    但**规则自己写错没人管**。探针实测（临时插一条 `{"table": "enemy_base", "column": "def_phsyc"}`）：
    - `row.get("def_phsyc")` 返回 null，`float(null)` **当场报运行期错误**；
    - `_check_ranges` 由此**中途中断**，它后面的规则（`res_poison` 那条上限）**一条都没跑**；
    - 而 `validate()` 的调用方只看到「错误少了一条」——**最危险的不是报错，是后面整段校验静默不执行**。

    两处修法：① `_check_ranges` / `_check_relations` 加守卫——先用 `_has_property()` 核对列名
    （经 `Registry.property_of` 解析别名），列名对不上就报「校验规则里的列不存在：X.Y（RANGES 写错了）」
    并 `continue`，后面照常查；② `test_table_pipeline` 加一条自检用例，遍历四张规则表，
    要求点到的**表名与列名全部真实存在**（这类规则是几十轮里加的，写错太容易）。
    验证：断言 5704 → **5705**。**反向验证**：把那条拼错的规则插回去 →
    自检立刻报 `RANGES：enemy_base 没有列 def_phsyc`；同时探针显示守卫生效
    （三条消息都在：负防御、列不存在、超额抗性），不再中断。

147. **主键 `index` 校验越界，会把整段主键检查掐断**（决策 145 同一天发现的第二处，同一个家族）。
    起因很平常：跑验收时在输出里瞥见两行
    `SCRIPT ERROR: Out of bounds get index '19' (on base: 'Array')` ——
    **自检却是绿的**，所以先当噪声放过去了。追下去才发现它不是噪声：
    `TableValidator._check_primary_keys` 里那句 `rows[position]`，`position` 直接取自资源里的
    `index` 字典，**没人保证它在 `rows` 范围内**。`index` 与 `rows` 对不上时位置恰好越界
    （删过行没重建索引就会出现），Godot 当场报运行期错误并**掐断整个函数**——
    排在 `level_growth` 后面的二十多张表，一条主键错都不会再查。

    探针把它钉死（临时脚本，用完已删）：同时把 `level_growth` 与 `item_base` 的第一行删掉、
    **不动 `index`**，然后跑 `validate()`：
    - 修之前：只报出 `["level_growth"]`（共 21 条错），`item_base` 一条都没有，附带
      `Out of bounds get index '19'`；
    - 修之后：报出 `["level_growth", "item_base"]`（37 条错），没有运行期错误。

    修法：把 `position >= rows.size()` 也算作不一致，报一条
    `X 的 index 与 rows 不一致：Y（index 记位置 N，实际 M 行）`，然后**继续查后面的行与表**。
    用例 `test_table_pipeline._check_stale_index_is_caught` 同时弄坏两张表，要求两张都被点名、
    且错位条数 > 2（逐行点出，不是只报一条）。验证：断言 5705 → **5708**。
    **反向验证**：把守卫改回 `position < 0 or rows[position] != row` → 用例红，
    消息正是「排在其后的 item_base 也要被查到——越界曾把整段主键检查掐断（实报：["level_growth"]）」。
    顺带一个观察：修完之后 `.logs\tests.log` 里的 `SCRIPT ERROR` 从 2 条降到 **0 条**，
    于是有了 148。

148. **把「引擎日志里有运行期错误」做成门限，并给 `--script` 步骤加 `--quit-after` 兜底**。

    **「日志里有没有运行期错误」这条从来没被验过**，而验收的三道网（退出码、`SELFCHECK: OK` 标记、
    按文件的「静态断言点 vs 实际执行条数」）在下面这个场景里全都会放行。两层探针证据：

    ① **运行期错误会让 `--script` 进程永远转下去**。写了个故意越界的 `--script` 探针：
    错误发生在 `_initialize` 里，于是 `quit()` 那一行根本没跑到，SceneTree 一直迭代

    判定标记由前面的代码打印，出错在它后面。

    实现：新增 `tools\check_log_errors.bat`（纯 ASCII + CRLF，走既有的「日志标记即真相」纪律），

    验证：`tools\run_all_checks.bat` 仍 **16/16 全绿**（新门限没有误伤；

    `tools\run_tests.bat` 报
    `[FAIL] .logs\tests.log contains a GDScript runtime error -- the check that hit it stopped early:`
    并回传退出码 1，探针已删、`run_tests.gd` 已按哈希核对还原。

150. **文档比对的「覆盖门限」：解析到 0 行要判错，不能报成「0 处不一致」**。
    `validate_tables.ps1` 的 5.26／5.29／5.30 是「按文档表格的排版解析出整行，再跟数据逐格比」。
    这类检查有同一个形状的洞：**文档一改版式**（加一列、换表头、多一行说明、全角竖线），
    解析就变成 0 行，比对循环一行都不跑——报出来的是「不一致 0 处」，**和真比过一模一样**。
    今天它在输出里只表现为一行 `文档定表 : 伤害类型逐格比了 0 行×7 列（不一致 0）`，
    而没有任何门限：5.26 那唯一一条真不一致（内伤吃不吃内防）会跟着一起消失，
    验收照旧 PASSED。「检查没做」被当成了「检查通过」——和版式预算／进程泄漏是同一条纪律。

    做法：加 `Assert-DocCoverage`，把「文档那一节到底比了几行」纳入门限——**0 行 = 这项检查没做 = 报错**；
    同时把覆盖写进输出行（现在是 `7/7 行`、`9/9 格`），人一眼能看出有没有缩水。
    为什么是报错而不是警告：**格与格不一致**属于「改哪边由设计定」（继续走警告），
    而**一行都没比到**是开发侧自己的解析坏了——两件事的归属不同，混在一起就是这次差点漏掉的原因。

    为什么只补三处：这五处文档比对里，5.27（明雷分布）与 5.28（副本房间）**自带反向循环兜底**——
    解析 0 行会把数据里每一个明雷／房间都报成「文档没列」，吵得很响、盖不住；
    **静默的只有 5.26／5.29／5.30**，这轮补的就是这三处。

    验证：实跑 `validate_tables.ps1` 仍 PASSED（覆盖 `7/7`、`9/9`），警告数不变（29 条）。
    **反向验证**（给 `-Root` 指向临时目录的副本，**不动真设计文档**）：
    ① 把 04 的伤害类型表与相克表各加一个竖线 → 输出 `0/7 行`、`0/9 格` ＋ 两条错误 ＋ FAILED ＋ 退出码 1；
    ② 把 01 的扩充分向表加一个竖线、把 `event_check.check_source` 的 `attr:`／`skill:` 前缀改掉 →
    另两条错误照样报出（三处调用点逐个验过，不是只定义了函数）。

155. **查 `damage_resolver` 那 11 个兜底常数**：9 个与表一致（不动），抓到 1 处「表说无上限、代码偷偷加上限」。

    先把「代码兜底 vs 表」逐条对了一遍（写脚本比，不靠眼睛）：

    | 代码常量 | 表里的对应值 | 今天 |
    |---|---|---|
    | `RNG_MIN/MAX_VARIANCE_DEFAULT`／`DEF_BASE_DEFAULT`／`DEF_LEVEL_FACTOR_DEFAULT`／`CRIT_BASE_MULT_DEFAULT` | `combat_const` 的 `variance_min`／`variance_max`／`def_const`／`def_level_coeff`／`crit_base_mult` | 5 条全等 |
    | `PEN_RATE_CAP_DEFAULT`／`BLOCK_RATE_CAP_DEFAULT`／`BLOCK_REDUCTION_CAP_DEFAULT`／`DMG_REDUCTION_CAP_DEFAULT` | `stat_def` 四个比率的 `max_value` | 4 条全等 |

    **这 9 条故意不加「代码 = 表」的断言**：`combat_const` 那 5 个兜底只在**表缺行**时才会用到，
    而校验器本来就要求这些行必须存在；给它们加一致性断言，等于让策划调一下 `def_const` 就得改代码——
    正常调数值不该被门限拦。口径写在这里，免得下一轮探针又把它当洞。

    **真正的问题在另外四个上限上**：`_stat_cap(stat, fallback)` 在 `stat_def` 那一行**没写上限**时返回兜底值，
    而这张表的约定是「`max_value` 留空 = 0 = **无上限**」（`stat_def_row.has_max()`、`curve_evaluator`、
    校验器三处都是这么写的）。也就是说：设计把 `dmg_reduction.max_value` 清空、意思明明是「不设上限」，
    跑起来却是 **0.6**——表与行为分家，**没有任何地方会红**。今天四个值都写着上限，所以是**潜伏**状态。

    修法：新增 `table_validator.REQUIRED_CAPPED_STATS`（穿透／格挡率／格挡减伤／减伤），
    每次构建与验收都要求这四个比率**必须写上上限**；报错文案直接说清「留空会让代码静默换用兜底常数，
    要么补上限、要么明确告诉开发侧改成无上限」。`damage_resolver` 那四个常量旁边也补了同一句话。

    顺带确认两个**不是**重复的定义：`HIT_CHANCE_MIN`／`HIT_CHANCE_MAX`（0.05／0.99）夹的是**最终命中率**，
    与 `stat_def.hit_rate.max_value`（0.95，夹的是属性本身）语义不同——别把它俩「统一」掉。

    验证：断言 5729 → **5730**（新增 1 条负向用例：内存里把 `pen_rate.max_value` 改成 0，要求校验报错）。
    **反向验证**：临时去掉 `validate()` 里的 `_check_pipeline_caps` 调用 → 自检当场红
    （`[FAIL] [数据管线与校验] 管线用的比率没写上限（留空='无上限'）应被校验抓到`），
    说明这条用例真的盯着调用点、不是同义反复；改回后按 SHA256 核对还原。

164. **难度表：只查了「> 0」，没人管难度是不是真的更难**。

165. **「算法在代码、常数在表」的另一半：代码点了名的常数，表里少一个只会静默用兜底值**。
    接着 164 往下扫，这次盯的是那两份**手抄的常数清单**。

    现状：成长系统（`GrowthCalculator`）与战斗管线（`DamageResolver`）都自带"缺行兜底默认值"——
    表里漏一行**不会崩**，只会静默用兜底值。PS1 那半边有两份手抄清单（成长 14 个、战斗 5 个）盯着，
    今天三边（代码 / 清单 / 表）**完全一致**，没有现存缺口。但**手抄的东西会漂**：
    代码里新加一个常数、清单忘了加，缺行就又变回静默。

    修法是把清单的来源换个方向——**以代码为准**，两边各取一次：

    - **成长常数**：代码里有集中清单（`GrowthCalculator.DEFAULTS` 的键），所以放进构建期校验器
      （`_check_growth_constants_present`）：表里少一个就报错，并指出"缺行会静默用兜底值（X）"。
    - **战斗常数**：代码里**没有**集中清单，名字散在 `constant("<id>", 默认值)` 的调用点上，
      所以放进 `test_handshake._check_code_constants_exist_in_tables`——**扫源码把实参抓出来**逐一对表。
      放测试里的另一个理由：导出后的包里不一定有 `.gd` 源码，**运行期不该依赖读源码**。

    验证：断言 5803 → **5811**。两条都做了负向验证——
    **成长**：内存里把 `mastery_max` 改名 → 校验器报「缺少代码依赖的常数 'mastery_max'」（并进了常驻探针，
    现在构建期 **37 个 case 全抓住**）；**战斗**：临时把 `combat_const.csv` 的 `def_const` 改名 →
    自检报 `[FAIL] combat_const 缺少代码依赖的常数 'def_const'`，改回后按备份还原核对。

    顺带说明为什么**没有**去动 PS1 那两份清单：它们各自也管着别的检查（成长清单那条还兼查
    `growth_const` 的行内容），删掉会丢覆盖面。两份清单与代码清单**今天一致**，而新加的两条门限
    能保证"代码新加常数时，缺行一定会被发现"——这就是原来担心会漂的那半边。

173. **「加了字段忘了存」给它加一道机器兜底**（存档字段）。
    顺着 172 的思路问下一个问题：06 那本数据字典漏列有门限了，那**存档字段**呢？

    那个字段每次读档静默回到默认值，玩家看到的是"我明明买了/学了，怎么没了"。

    `migrated_from`／`pruned_characters`／`reclaimed_equipped` 三个**读档整理结果**

    （它有自己的一份 `to_dict/from_dict`，同一个坑）。

    验证：断言 5995 → **6027**。
    **反向验证做了两次**：① 给 `GameState` 加一个 `var quest_state: Dictionary = {}` →
