178. **白名单全线体检：三份都补上"反方向"**（177 的续集）。
    177 给 `TEST_ONLY_API_ALLOWED` 补了反向检查，这轮把**其余三份**也补齐——同一个纪律：
    **白名单除了"条目还有效吗"，还要问"这条还配留在白名单里吗"**。

    | 白名单 | 原来只有 | 补上的反方向 |
    |---|---|---|
    | `SKIPPED_CHECK_WHITELIST`（假绿豁免） | 条目**必须**真的在漏跑断言，否则报假绿 | 条目对应的文件**已经不需要豁免**（实际执行数追平静态断言点）→ 报"把这条删掉"；文件不存在也报 |
    | `ROOT_SCENE_WHITELIST`（根目录孤儿场景） | 文件不存在 → 报"删掉这条" | 文件**已经被引用** → 报"删掉这条"（它是"暂时没人引用的编辑器草稿"，一旦接上就该退场） |
    | `INFRASTRUCTURE_TESTS`（不参与孤儿检查的用例） | 只用来跳过孤儿检查 | 白名单里的**文件必须存在**（名字写错／文件删了都得报） |

    复用别的检查的语料很容易问错问题。

179. **成长常数也有"可用下限"——低于它就被代码静默换掉**（155 那个家族又一处）。
    178 之后换了个方向：不再审白名单，而是**照着代码里的守卫反查表**。
    `GrowthCalculator` 里有几处守卫，它们同时意味着"表里写了更小的值也没用"：

    | 常数 | 代码里的写法 | 写小了会怎样 |
    |---|---|---|
    | `active_slot_lv_div`／`active_slot_attr_div`／`passive_cap_lv_div`／`passive_cap_attr_div` | `maxf(值, 1.0)` | 除数被**换成 1.0**——容量曲线整条变样，却没有任何提示 |
    | `cultivate_cost_growth` | `pow(值, 等级-1)`，**没有守卫** | 负数底数会算出**负费用**（打坐反而给你钱） |
    | `codex_step`／`codex_cap`／`mastery_max` | `maxi(1, ·)`／`maxi(0, ·)`／`clampi(·, 1, maxi(1, ·))` | 同样是被静默换掉 |

    新增 `_check_growth_const_ranges`：给这 8 个常数各写一条**可用下限**，
    报错时把"为什么是这个下限"一起说出来（即代码里那句守卫）。下限值不是编的——
    每条都在注释里指明了它对应代码的哪一行写法。

    验证：断言 6055 → **6056**（一条负向用例同时塞两处越界，要求各报一条）。
    **变异探针加两条**：`cultivate_cost_growth = -1.6`、`active_slot_lv_div = 0` 都被抓住

181. **"代码里有一份列表、场景里有一套节点"的地方：两面都要对齐**（商店页签先做）。
    180 之后我说要扫 UI 层，这一轮真去扫了。先说结论：**UI 里的 `mini/maxi/clampi` 没有发现问题**——
    它们要么是内部保护（血条除零用 `maxi(1, 血量上限)`、数量钳制），要么是被文档写明的**有意截断**
    （战报卡片固定 3 行、超出进战报）。同时也确认 `src`／`tools`／`tests`／`scenes` 里
    **一个 TODO/FIXME/HACK 都没有**（这个项目的习惯是把缺口写进 dev 文档，不在代码里留小旗子）。

    但顺手量到一个真空白：**"代码里一份列表 ↔ 场景里一套按钮"这类结构，只有单向检查**。
    场景节点契约那条门限管的是"代码 `_require_node` 要的节点必须存在"；
    **反过来（场景里有节点、代码却不认）没人管**。而商店的页签正好是这种结构的典型：

    - `shop_screen.gd` 的页签来自常量 `TABS`，绑定时用
      `_tabs_box.get_node_or_null("Tab%s" % 后缀)`——**取不到就静默跳过**；
    - 自检偏偏是 `select_tab(key)` **直调**（不需要按钮存在），所以
      **"TABS 加了第五个页签、场景没加按钮"会全绿，而玩家点不到那个页签**；
    - 反向也一样：场景里多一个 `Tab*` 按钮，点下去什么都不做，没人报。

    新增 `_check_shop_tabs_have_buttons`：解析 `TABS` 的 key、`_tab_node_suffix` 的后缀映射与
    场景里的 `Tab*` 按钮，**三份对齐**——每个 key 都要有后缀映射和对应按钮；场景里每个
    `Tab*` 按钮也必须对应一个 key。行数／名字对不上都当场点名。

    验证：断言 6057 → **6069**。**两个方向都反向验证过**（一次跑出两条红）：
    把场景里的 `TabService` 改名 → 报"TABS 里的页签 service 需要场景里有 TabService 按钮
    （没有按钮＝玩家点不到，而自检直调 select_tab 照样绿）"；同时那个改名的 `TabProbeOrphan`
    被报"场景里的按钮在 TABS 里没有对应页签（点了什么都不做）"。改回后复验绿（按备份还原）。

    留一句给后续：这类"**代码列表 + 场景节点**"的结构别处可能也有（比如角色面板的页签、
    完成度面板的楼层行）。要加同类门限时，先把"列表在哪、节点名怎么拼"两处都写清楚再动手——
    这轮的教训是**自检直调 API 会绕过"按钮存不存在"**，光看自检绿是不够的。

183. **「待办清单」自己的编号也要有门限**（Q 清单：重号／悄悄删一条／范围写旧）。
    182 讲的是**代码侧**硬编码清单；这一轮是它的**文档侧同胞**，而且是复查引擎侧视角时顺手撞到的：
    `当前状态.md` 开头那句「一句话就能回的问题（**Q1–Q31**）」——Q 清单**早就长到 Q36**，
    这句没人改，**而且没有任何检查会红**（清单越补越长，这句就越是假话）。

    这类待办清单最怕三种烂法，**都静默**：

    ① **重号**：两条问题共用一个编号，引用它必然指错一边；
    ② **悄悄删条**：问题被删掉、编号空着，读的人以为清单还是完整的
       （158／159 两轮治的就是"清单看着完整、其实漏了大半"）；
    ③ **范围写旧**：像上面那句 Q1–Q31。

    加 `_check_question_numbering`（`tests/test_handshake.gd`），三条一起钉：

    - Q 行编号**不重**（按 `| Q<数字> |` 收行）；
    - **1..最大编号里缺的那些**，必须与「编号说明」里的 `**跳号登记**` 那行**一一对应**——
      `Q28` 是开发侧结案移除的、编号空着不挪；以后谁再**悄悄删一条**当场红，
      **登记了又补回来**也红（那条登记得跟着删）；
    - 两份**现状文档**（`当前状态.md`／`待策划确认.md`）里写的 `Q<起>–<止>`，止必须等于真实最大编号。
      **`框架说明.md` 故意不在其中**：这里记的是带日期的叙事（"那天补到哪"），
      拿现状口径去量它会假红（同 182 那句"功能清单 vs 手感值"的分别）。

    **反向验证**（一次跑出四条红，四条都是真问题）：把 `当前状态.md` 的范围改回 `Q1–Q31`
    ＋ 抽掉 `Q36` 那一行 ＋ 清空跳号登记 → 报
    「这些编号既没有对应的问题、也不在「跳号登记」里（被悄悄删了？）：Q28」／
    「`当前状态.md` 里写的 Q 范围「Q1–Q31」止于 Q31，而 Q 清单最大是 Q35」／
    「`待策划确认.md` 里写的 Q 范围「Q32–Q36」」「「Q1–Q36」止于 Q36，而 Q 清单最大是 Q35」；

    1 条"缺号必须登记"＋1 条"登记的又回来了"＋3 条"文档范围逐一核对"＋1 条"至少写明了范围"。

    `const TableDbScript := preload(...)`，而 `TestCase` 基类已经有这个名字 → 整个用例文件
    **Parse Error: The member "TableDbScript" already exists in parent class**，
    自检直接报「test_handshake.gd 无法加载」。**基类已有的常量直接用，别在子类里重声明。**

    累计：断言 6070 → **6079**（Q 编号门限 9 条）→ **6085**（看板数字门限 6 条）→ **6086**
    （本段引了一处工具路径，被"开发文档里引到的工具必须真的存在"那条数了进去——同 182）；
    全量验收 16/16。

    再记一条"看门狗"的口径（同一轮顺手量的，写进了脚本注释）：`tools\run_all_checks.bat`
    最后那步「不许留下引擎进程」查的是 **`GODOT_BIN` 的文件名**——而那个 `*_console.exe`
    只有 **198 KB，是个启动器**；真正的引擎是 179 MB 的 `Godot_v4.7.1-stable_win64.exe`，
    作为它的子进程在跑（实测：跑起来时两个都在，只杀启动器、子进程跟着没——console 一关它就跑不了）。
    所以"启动器还活着"是"跑漏了一个"的**有效代理**，而**反过来照引擎名去查是错的**：
    编辑器进程用的正是引擎那个名字，一查就会把用户自己开着的编辑器算成泄漏（假红）。
    这条写进脚本注释了，免得后来的人"顺手优化"成引擎名匹配。

    顺带一条工具口径（同一天复查 MCP 时踩的）：**探 MCP 服务必须 `POST /mcp` 带 JSON**。

    其实那个服务**只处理 POST**，连上不答就是它的正常反应。`netstat` 能看到端口在听、
    请求发对了立刻有回（`initialize`／`tools/list`／`get_project_info`／`list_scenes`／`get_scene_info` 全部正常），
    这条写进了 `README_MCP.md`。**"量不出来"不等于"东西坏了"**——同一条纪律，换个场景又撞了一次。

212. **buff 结算落地：常驻走贡献通道，临时走现算**（0.7.0／0.8.x 的「需返工」大头）。

    只是静态规则。这轮把它接进战斗，拆成**两条互不重叠的路径**：

    - **常驻 buff（`duration=0`）→ 贡献通道**：装备 `on_equip`（锈月／前代寨主遗物）与套装档位

      与 `CharacterSheet.set_contributions()` 各接一处。这样「装备即生效」在**角色面板与战斗里是同一个数**，
      不需要第二条结算路径；贡献的 `source` 写成 `buff:<buff_id>@<装备实例 id>` / `set:<set_id>`，
      与装备自己的 `bonus_*` 列（source = 实例 id）分得开，用例能逐条钉值。

214. **Godot MCP（编辑器插件，端口 3001）能用来做什么、什么绝对不能碰**。
    本项目挂着 `addons/godot-mcp/`，用 `POST http://127.0.0.1:3001/mcp`（JSON-RPC）驱动。
    这轮按「多用 MCP 做调试」的要求把它摸清了一遍，结论写成一份可复用清单：

    | 工具 | 能不能用 | 说明 |
    |---|---|---|
    | `get_project_info` | ✅ 只读 | 实测回 `godot_version 4.7.1-stable / renderer mobile / main_scene res://scenes/main_menu.tscn`，与 `project.godot` 一致 |
    | `list_scenes` | ✅ 只读 | 实测列出 18 个 `.tscn`——把代码里引用到的场景路径逐个对上（比 `ls` 更接近引擎看到的资产表） |
    | `get_scene_info` / `get_node_property` | ✅ 只读 | 报**编辑器当前打开的那个场景**；它开着 `main_menu.tscn`，`get_node_property(path=".", property="script")` 实测回 `res://src/ui/main_menu.gd`——**场景与脚本的绑定对得上**。**但别指望它核对节点名**：`get_scene_info` 那次只回了 `MainMenu` 一个节点，一开始我以为是工具只给根节点，**对完文件才发现那个 .tscn 总共就一个节点**（359 字节，菜单 UI 全在 `main_menu.gd::_build_ui()` 里建）——也就是说「工具给了什么」要看当前打开的场景本身长什么样（2026-10-03 修正这条说明：原来的写法会让人以为它能核对整棵树） |
    | `add_node` / `set_node_property` / `save_scene` | ⚠️ **别用** | 它们只作用于**编辑器当前打开的场景**，而工具集里**没有"打开某个文件"**——想改 `battle_screen.tscn` 却可能改到 `main_menu.tscn`。改场景一律用 `apply_patch` 直接写 `.tscn`（本轮两行新节点就是这么加的） |
    | `run_project` | ❌ **别调** | 之前实测会把插件卡死；跑场景用 `tools\check_scene.bat`（headless）或 `tools\run_windowed_smoke.bat`（真窗口） |

    **一处已知不统一**（记在这里，别当 bug 去「顺手统一」）：面板类界面（战斗／角色／商店／打坐／驿站／线索本／完成度）
    都是「骨架进 `.tscn`、代码只做绑定」，而**启动菜单除外**——它整棵 UI 在 `main_menu.gd::_build_ui()` 里建。
    菜单有自己的真场景自检与闭环里的真按钮流程盯着（新建／读档／退出／槽位），**没有可见缺陷**；
    要不要把它也搬进 .tscn 属于纯内部整理，等有实际改动需求时再说。

    两条纪律：① 编辑器进程是用户开着的（本轮一直在跑），**不要杀**；② 只读那四个工具适合做**交叉验证**
    （项目设置、场景清单、当前场景结构），真正的"制作"仍然走文本文件 + 自检命令——那条路有 6900+ 条断言兜底，
    而 MCP 的写接口没有。
