# 10 敌人与技能配表

## 一、敌人招式改为配表驱动

**现状**：敌人用什么招写死在 `src/core/enemy_factory.gd` 的 `AI_SKILL_MAP` 里，
按 `ai_template` 映射。结果是 **14 个敌人里 12 个只有 1 招**，而且全是 ★1 基础招，
只有两个 Boss 有 2 招。

**问题**：设计 04 的核心循环是「敌人出招前有预兆，玩家可以拆招」。
可如果敌人**每次都出同一招**，预兆就没有信息量，拆招也不需要判断——
看一眼就知道，然后每回合照做。**这套机制只有在敌人有多招时才能成立。**

**改法**：新增 `enemy_skill.csv`，把「谁会什么」从代码搬进表。

| 字段 | 说明 |
|---|---|
| `enemy_id` | 引用 `enemy_base` |
| `skill_id` | 引用 `skill_base`（数值走 `skill_active`） |
| `sort_order` | 顺序，仅用于展示与稳定排序 |
| `note` | 备注 |

配表原则：**杂兵 2 招、精英 2–3 招、Boss 3 招**。
每多一招，预兆就多一分不确定性，拆招才成为一个判断而不是一个习惯。

同时把三个单调感一起解掉：

- **近战与远程搭配**：弓手只有远程招，刀客只有近战招，站位与集火目标因此有差别
- **单体与群体交替**：Boss 的斩风（单体高伤）与横扫（三段全体）交替，
  玩家要在"这一回合谁会被打"上做判断
- **异常状态由敌人主动施加**：毒手会上毒，玩家得考虑解毒或速杀

## 二、敌人的属性模板与角色一致

**现状**：`enemy_base` 直接给派生数值（`hp_base`／`atk_phys`／`def_phys`／
`speed`／`hit_rate`／`dodge_rate`／`crit_rate`／`res_*`），角色走的是
「七维 → `attr_to_stat` → 派生数值」。
**两套数值系统并行**，调平衡时要分别估、分别改，而且同一件事有两处定义。

**改法**：`enemy_base` 改用与角色相同的模板——

```
敌人七维 + 等级 + 武器类型  ──►  attr_to_stat / level_growth  ──►  派生数值
                               └─ 与角色完全同一条管线 ─┘
```

新列：`attr_str` / `attr_con` / `attr_agi` / `attr_int` / `attr_luk` /
`attr_wu` / `attr_gen`，与 `character_base` 同名同义；`level` 沿用现值。
`difficulty_config` 的倍率照旧在最后乘。

### 三条连带规则

**敌人同样受招式槽与内功容量限制。** 悟性决定能带几招、根骨决定能带几格内功，
用的是 `growth_const` 里同一组公式。**校验器会检查「配的招式数 ≤ 槽位上限」**，
配了 5 招却只带得动 3 招会在构建期报错，不会静默超编。

**抗性不再单列。** `res_poison` / `res_burn` / `res_bleed` 这几列取消——
角色那边本来就没有对应的属性来源，敌人也不该有特权。
需要抗性的敌人（比如毒手）**装配一部内功**来获得，与角色同规则。

**敌人也要有内力池。** `enemy_base` 补 `qi_max`（或由智/根骨派生）。
现在敌人 `qi_max = 0`，而 `_is_usable` 里"内力不够就不能用"对 `max_qi()==0`
的单位直接跳过——**高消耗招式对敌人是免费的**。现在看不出来是因为敌人
只有 ★1 招；一旦按本方案配上高星招式，它们会无限放。

## 三、这一步的代价与顺序

这是**结构性改动**，不是加两列：

| 面 | 改动 |
|---|---|
| `enemy_base.csv` | 列全换（派生数值 → 七维），14 行数值重配 |
| `enemy_base_row.gd` | 重写 |
| `EnemyFactory` | 删除 `AI_SKILL_MAP`／`ENEMY_SKILL_OVERRIDE`，改读 `enemy_skill`，并按角色同款管线算属性 |
| 平衡观测 | 全部数值要重跑一遍 |

**第一步先只做「招式配表」**（第一节，已完成）。
它单独就能修好"敌人只有一招"，而且不动属性管线，风险最低。

**第二步再动属性模板统一**（第二节）。它要重配 14 个敌人的七维，
而数值必须用开发侧的平衡观测工具反复校准——**盲配一遍再让工具报红，
不如拿着工具配**。所以这一步的开发顺序是：先改 `EnemyFactory` 与表结构，
跑通空数据，再一起配数值。

## 四、敌人装配装备，且穿什么掉什么
### 架构边界：同模板，分开处理

敌人和角色**共用一套模板，但数据与流程各自独立**。这句话要写清楚，
因为「统一」很容易被读成「合并成一张表、走同一条流程」——那不是本意。

| 面 | 共用 | 分开 |
|---|---|---|
| 属性模板 | 七维字段名与含义一致 | 两张表：`character_base` / `enemy_base` |
| 派生数值算法 | `attr_to_stat` ＋ `level_growth` 同一套 | — |
| 招式数据 | 同源 `skill_active` | 角色走 `character_base_skill` ＋存档；敌人走 `enemy_skill` 配表 |
| 装备数据 | 同源 `equip_base` | 角色走背包＋存档；敌人走 `enemy_equip` 配表 |
| 内功数据 | 同源 `skill_passive` | 角色走 `skill_loadout` ＋存档；敌人走 `enemy_passive` 配表 |
| 难度倍率 | `difficulty_config` | 只作用于敌人 |

**分界的根源只有一条**：

> **角色是「玩家可变的运行时状态」，敌人是「配表固定的定义」。**

角色的等级、加点、熟练度、装备、装配全在存档里，玩家随时能改；
敌人的这些全是构建期定死的，每次战斗按表即时构造、战斗结束即丢。
两者的**形状相同、来源与生命周期不同**，所以共用算法、分开存数据。

这条边界也是后面加东西的判断依据：**新属性、新招式、新装备**加到共用那几列；
**"玩家怎么获得、怎么装配、怎么存"**加在各自那一侧。

## 五、敌人装配装备，且穿什么掉什么

**敌人和角色一样有 7 个装备槽**，配置见 `enemy_equip.csv`。

### 核心规则：身上穿的，就是能掉的

**敌人的装备掉落不再单独配，直接从 `enemy_equip` 推。**

| | 做法 |
|---|---|
| 掉落来源 | 敌人身上每一件装备，按稀有度概率掉落 |
| 概率 | 复用 `rarity_def.drop_weight`，不另设一套 |
| 首杀 | **首杀必掉一件**（保住「首杀有确定的惊喜」这条设计） |
| `drop_table` | **不再列装备**，只留材料、铜钱、秘籍 |

好处是玩家能**看见就懂**：那个刀客挂着黑风刀，那就去打他。
不需要查掉落表，也不需要在攻略里对 id。

而且这条消除了一个隐患：原来「敌人身上的装备」和「掉落表里的装备」是两处定义，
改了装备忘了改掉落，玩家就会看到「他用着青锋剑却掉柴刀」。

### 装备同时影响敌人属性

敌人属性 = **七维 ＋ 等级 ＋ 装备加成**，与角色完全同一条管线
（`Inventory.contributions_for` → `AttributeCalculator`）。

所以给 Boss 换一件装备，他的强度和掉落**一起变**，不会脱节。

### 连带改动（开发侧）

`drop_table` 里这 12 行**要删掉**——它们都是「敌人身上装备」的重复定义：

```
dr_wolf_03  dr_thug_04   dr_archer_02  dr_elite_02
dr_elite_03 dr_lwolf_02  dr_lwolf_03   dr_ph_04
dr_butcher_02  dr_boss_02  dr_boss_04  dr_drunk_02
```

**宝箱掉落不动**（`dr_chest_*`）——箱子里的东西是探索奖励，与敌人穿什么无关。

`dr_boss_02`（首杀必掉黑风刀）删掉后，它的保证**由「首杀必掉一件身上装备」接管**，
大寨主身上挂的就是黑风刀，效果不变。
